# note-merge-section · 参考材料（分节融入的设计论证）

> 本文件是技能 `skills/note-merge-section/SKILL.md` 的**配套参考**，不会被送进模型 ——
> 送进模型的只有 SKILL.md 正面（frontmatter 之外）的内容。这里保留"为什么这么切"的论证。

## 一、为什么要把「融入」拆成两步

原来的实现只有一条路：让模型读**整篇**、输出**整篇**（`skills/note-merge/SKILL.md`）。
这条路在短笔记上质量最好（能跨节重排、去重），但输出量 = 整篇正文字数，
所以长笔记必然撞输出上限，于是后端加了一道 16000 字的闸门（`AgentService.MERGE_MAX_CHARS`），
长笔记直接融不进去。

关键认识：**"放哪儿"需要看整篇（输入），"写什么"只需要落到那一节（输出）**。
把输出范围从"整篇"缩到"一节"，闸门就没有存在的必要了 —— 输入侧从来不是瓶颈。

## 二、为什么这比"整篇重写"更安全，而不是"将就"

整篇重写有一个**无法从预览里发现**的失效模式：模型漏掉一节、少写一段，
产出仍然是一篇"看起来完整"的笔记。这正是 16000 闸门想拦的东西
（原文：*截断的结果看起来像是完成的*）。

分节路径把这个风险换掉了：

1. **未被选中的部分根本不进模型的输出**。不是"模型保证不改"，而是"模型没有机会改" ——
   补丁只替换目标小节的字节区间，其余部分逐字来自原文。
2. **截断只可能发生在这一节**，而且长度下界一比就知道（`min_ratio`，与整篇路径同一套闸门）。
3. 贴补丁前会核对原文（`applySectionPatch` 里 `section.text` 与实际区间的比对）：
   用户在模型跑的过程中改了字、或切换了笔记，就直接放弃并报错，不会覆盖到别处。

所以这条路径**同时**做到了"长笔记能用"和"更不容易悄悄丢内容"。

## 三、为什么是两个技能文件

- `note-merge-locate`：输出必须**极小且结构化**（一个 JSON），它不需要融入规则，
  只需要判断主题归属。把融入规则塞进它的提示词只会让输出变长、变不稳。
- `note-merge-section`：承载完整的融入规则（与整篇版的六节规则同源），
  但它面对的是"一节"而不是"整篇"。

两个技能都遵循 `SkillService` 的约定：**找不到技能文件就报错，不静默回退到内置常量**
（静默回退会让用户以为改动生效了，实际跑的还是旧提示词）。

## 四、几个具体取舍

| 取舍 | 选择 | 理由 |
| --- | --- | --- |
| 定位的返回形式 | **编号**（`index`），不是标题文本 | 笔记里完全可能有两节都叫「其他」；编号由我们生成，不会歧义 |
| 标题行归谁 | 标题行**不进模型的输出**，由补丁原样保留 | 模型最容易犯的错就是把标题抄一遍/改写一遍；不给它机会。`SKILL.md` 里也明写了这条 |
| 大纲给什么 | 标题 + 字数 + 子标题 + 开头一句 | 定位看的是结构；把整篇正文塞进定位那一步，就白拆了 |
| 单节过大怎么办 | 退化成 `insert`：只产出新增的 `###` 子小节 | 子小节的内容量由"新内容"决定，与被改写的节多大无关，输出始终有界 |
| 没有可用标题的笔记 | `append`：在末尾新增一节 | 兜底也要**说清楚**（预览会写明"新增一节"），而不是偷偷改成整篇重写 |
| 阈值 | 8000 字（`SECTION_REWRITE_MAX`） | 与后端 32768 的输出上限、以及整篇路径 16000 的闸门同一量级：留足"原文 + 新增"的余量 |

## 五、没有采用的做法

- **把整篇按节切开逐节重写再拼回去**：等于让模型把每一节都输出一遍，
  没被新内容涉及的节也被重写了一次 —— 既贵，又白白引入"重写走样"的风险。
- **给长笔记提高输出上限**：上限由模型决定，不是配置能解的；而且截断的风险原样存在。
- **让智能体用 `edit_note` 工具自己插**：那条路已经能用（用户可以直接对智能体说
  "把上面这段并进第 4 节"），但要走完整的工具循环（更贵更慢），且依赖模型选对工具；
  它是应急出路，不是「融入当前笔记」这个按钮的默认实现。
