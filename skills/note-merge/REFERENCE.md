# note-merge —— 把回答按结构融入笔记（给人看的）

`SKILL.md` 是送给模型的提示词，本文件是配套参考：为什么"融入"要交给模型做、边界在哪、
怎么调、以及验收要点。**不会送进模型**。

## 为什么不是"往文末追加一段"

第一版实现是把 `## 你问的问题 + 回答` 追加到正文末尾（简单、确定、零成本）。实际用起来的问题很直接：

- 一段"关于并发注意事项"的回答被贴到讲"基础语法"的笔记末尾，**知识和它的上下文分家了**；
- 同一主题被问两次，末尾就出现两段近似内容，笔记越长越难读；
- 用户下次翻这篇笔记时，看到的是"一串问答记录"，而不是"一篇讲这个主题的文章"。

所以改成：**由模型读完整篇 + 新内容，产出一篇把新知识放到该在位置的新正文**，
再由用户在编辑器里预览、点「替换正文」、点「保存」。

## 与仓库里其它"AI 改正文"的分工

| 技能 | 输入 | 输出 | 落点 |
| --- | --- | --- | --- |
| `markdown-polish` | 笔记正文 | 同一篇正文（措辞规范化） | 对话框预览 → 替换正文 |
| `markdown-beautify` | 笔记正文 | 同一篇正文（排版重排） | 对话框预览 → 替换正文 |
| **`note-merge`** | 笔记正文 + **新内容**（问答）+ 问题 | **变长的**完整新正文 | 对话框预览 → 替换正文 |

三者共用同一条链路：`AgentService` 读技能文件当 system 提示词 → SSE 流式返回 → 编辑器弹窗预览 →
用户点「替换正文」→ 用户点「保存」。**AI 从不自己提交**：它只把候选正文交到用户手上。

## 关键取舍

1. **一次整篇，不分段**。润色/整理格式按 4000 字分段是因为"逐段改写"不影响段落之间的关系；
   而"放到哪一节"必须看到**整篇结构**才知道，分段会直接把这件事做废。代价是笔记太长时输出会超上限 ——
   所以有长度闸门（见下）。
2. **长度闸门比润色更严**。润色允许缩到 60%（`min_ratio`），融入是**只增不减**的事情：
   `note-merge` 的 `min_ratio` 写 0.9，后端还会拒绝"比原文短"或"长得离谱（疑似重写/编造）"的结果，
   并在失败时**保持正文原样**（不静默append、不把半截结果塞进去）。
3. **超长笔记直接拒**（默认 16000 字）。一条 20 万字的书，把全文 + 新内容喂进去再要求整篇输出，
   必然被输出上限截断，而截断的结果看起来"像是完成了"——这是最危险的失败模式，所以宁可在入口就说清：
   *"笔记太长（N 字），整篇融入会超输出上限；请手动把这段贴到对应小节，或先用「整理格式」精简。"*
4. **冲突不改原句**。模型判断两种说法矛盾时，只在其后补一行 `> 补充（智能体）：…`，
   让人来判断谁对。知识库里"悄悄改掉原来的结论"是不可接受的行为。

## 验收要点（改提示词后按这个过）

拿一篇**有 2~3 个小节**的笔记试：

1. 新内容与**已有小节**同主题 → 是否并进那个小节（而不是新开一节）？
2. 新内容是**已有小节的延伸**（例如"坑"）→ 是否紧跟在该小节之后，且标题风格一致？
3. 新内容与原笔记**重复** → 是否只留一处？
4. 新内容与原笔记**矛盾** → 原句是否原封不动，只多了一行补充？
5. 原笔记的格式（列表标记、加粗、代码块、内联 HTML）是否原样保留？
6. 回答里的对话语气（"我帮你查了"）是否被改写成笔记体？
7. 输出长度是否 ≥ 原笔记（只增不减）？有没有凭空多出原文与回答里都没有的事实？

任何一条不满足，先改 `SKILL.md`（**存盘即生效，不用重启后端**），再考虑改代码里的闸门。
