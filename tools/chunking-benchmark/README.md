# 分块检索配对实验

本工具仅使用仓库内手工编写的合成中文学习资料与本机 Ollama，不读取知识库，不调用聊天模型，不更改应用设置。`fixture.json` 为冻结的 10 篇资料、31 个问题，问题标注的是正文证据字符跨度。`build_fixture.py` 是可读的生成来源；开始评测后不要按评测结果修改题库。

三种条件使用相同的 `qwen3-embedding:4b`、标题上下文前缀、原始查询与余弦排序：

- `legacy`：`legacy/TextChunker.java`，取自改动前 Git HEAD，提交号与 SHA-256 在 `legacy/baseline.txt`。
- `structural`：实际产品 `TextChunker.java`，结构保护分块。
- `semantic`：同一结构保护，对 `file` 且不少于 4000 字符的资料使用实际产品 `SemanticChunker.java`。仅非保护单元计算边界向量，断点百分位固定为 85。

工具通过 `javac` 将基线与当前产品 Java 分别编译到隔离目录，`ChunkExport.java` 调用真实实现。没有 Python 分块仿版，也不启动 Spring、数据库或额外 Ollama 服务。

运行前需要 Java/Javac、已解析 Jackson 依赖的本机 Maven 缓存、Python 及 NumPy，以及本机已安装的 Ollama 模型。

```powershell
python tools/chunking-benchmark/test_metrics.py
python tools/chunking-benchmark/run.py --batch 4 --budget 2400
```

默认输出 `results/report.json`、各组分块及逐题结果，缓存位于 `.work/`，两者已被本目录 `.gitignore` 排除。要测量一次新构建，可指定新的输出目录并将 `.work/vectors` 改名保存后重新运行。恢复运行会复用已有批次，并报告 `build_cached_batches`；报告中的时间是这些批次初次实测时间的累计，不是恢复过程的墙钟耗时。

评价不根据文件名或标题判定命中。先把块正文映射回同篇资料的正文字符位置，再与标注的证据跨度比较，忽略空白。若结构续块添加闭合围栏或重复表头，只映射长度至少 16 字符的原文匹配片段。证据命中要求至少覆盖答案证据的 20%，且至少覆盖 24 个字符（短答案使用全部证据长度）；完整覆盖要求每一个标注跨度的所有非空白字符均出现在已取回的正文中。

检索上下文预算固定为 2400 个原始正文字符，按向量排序遍历前 10 个候选，整块放入，剩余空间放不下的块跳过并明确记入 `blocked`，不截坏代码或公式。报告 Hit@1、Hit@3、预算内命中、完整覆盖、证据字符覆盖率与 MRR，并按内容类型分组。固定预算比较不等价于固定 Top-K，完整覆盖也不等价于某一个块含有整段答案。

构建时间包含分块、块嵌入，语义组额外包含边界嵌入。首次模型加载单列为预热时间。查询向量在三组之间复用以固定输入；查询嵌入时间是同一批量请求的摊销均值，排名时间单独计时，不能解释为线上单查询 P50 或完整回答延迟。没有混合召回、相邻块扩展、重排或回答生成，所以这是分块引起的纯向量召回对比，不是端到端答案正确率评测。31 题的小型合成数据不足以证明真实知识库的普遍收益。

`verify_final.py` 用于代码修复后的冻结结果确认：它先保留原始测量所用 `.work/current-classes` 导出的单元，再重新编译最终源码，逐项核对三组分块，并使用已缓存的原始向量重新评分。该命令不调用模型，不改写原始测量时间，输出单独的 `final-validation.json`。因此需要保留原始 `.work` 与 `results`；不要在丢弃原始类后把最终类冒充原始参考。
