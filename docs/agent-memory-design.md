# 智能体的记忆与检索 · 设计说明

> 实现位置：`backend/src/main/java/org/dyh/learnhub/service/AgentSessionService.java`（存储与投影）、
> `backend/src/main/java/org/dyh/learnhub/ai/AgentService.java`（模型调用与编排）、
> 表结构在 `backend/src/main/resources/schema.sql`。
>
> 这份文档记录**为什么这么做**以及**代价是什么**——代码注释讲单点，这里讲全局。

---

## 0. 改造前的问题

原实现是「服务端完全无状态 + 前端把最近 12 条历史带回来」：

1. **刷新即失忆** —— 历史只活在前端内存里；
2. **老消息无声消失** —— 超过 12 条直接截断，模型会突然"忘事"；
3. **后端没有审计线索** —— 出问题无从查起；
4. **知识库没被用上** —— 检索靠模型自觉调 `search_knowledge`，它经常想不起来。

---

## 1. 数据模型：事件流 + 投影

会话 = 一条 **append-only 事件流**；界面和模型看到的都是它的**投影**。

```sql
agent_session(id, title, note_id, created_at, updated_at)
agent_event(id, session_id, role, content, tool_name, tool_call_id, tokens, created_at)
```

`role` 的语义（关键）：

| role | 含义 | 是否参与上下文投影 |
| --- | --- | --- |
| `user` / `assistant` | 真实发生的一问一答 | ✅ 参与（只取最终文本） |
| `tool` | 一次工具调用与结果 | ❌ **不参与**，仅审计与界面回看 |
| `summary` | 对较早内容的压缩摘要 | ❌ 不直接参与，但它的**文本**会被单独注入 |

**为什么不用 `seq` 列**：同一会话内自增 `id` 天然单调，用它排序就不需要 `MAX(seq)+1` 查询，
也就没有并发下的竞态。跨会话比较顺序没有意义（查询永远按 `session_id` 过滤）。

---

## 2. 投影：模型到底看到什么

一次请求的上下文按顺序拼装（见 `AgentService#chat`）：

```
system    ：设置里的对话提示词（可在界面编辑）
user      ：「更早对话的摘要」（有 summary 时才加）
user×N    ：最近 8 轮 user/assistant 的最终文本
user      ：「自动检索到的相关记录」（有命中时才加）
user      ：本轮用户输入
```

**为什么不回放工具调用**：这是本设计最重要的一条取舍。
`search_knowledge` 一次就可能带回几万字的笔记片段，若在每轮把历史工具结果重放一遍，
上下文会被迅速撑爆、token 成本与延迟都不可接受，而收益（"记得自己上次查过什么"）很小。
工具事件留在库里，界面回看时会以角标形式还原（`messagesForDisplay`），信息没丢，只是不喂给模型。

## 3. 自动检索（RAG）

**触发**：每轮拼接上下文时，用本轮用户消息自动检索一次。
**召回**：`AgentService#autoRetrieve` —— 在笔记/速查卡的**标题与摘要**上做词面打分。

| 项 | 取值 | 理由 |
| --- | --- | --- |
| 打分 | 命中标题 **×3**、命中摘要/正文 **×1** | 标题是人为概括过的，比正文里的偶然出现更能说明相关性 |
| 注入条数 | 最多 5 条 | 多了会挤占上下文并稀释相关度 |
| 抽词 | ASCII 词 + 中文 2/3-gram（带停用词表） | 没有分词器时的常用近似 |
| 候选上限 | 最近 200 条 | 列表 VO 不含正文（LONGTEXT 不查），拉几百条也很轻 |

**四条明确的行为约定**：

1. **这不是语义检索** —— 没有向量、没有 embedding。个人库几百条，词面召回够用；
   要升级只需替换 `autoRetrieve` 一个方法（其余流程不用动）。
2. **全无命中就不注入** —— 注一段无关内容比不注入更糟（模型会硬往上靠）。
3. **检索失败退化为"不注入"** —— 记一条 warn，绝不影响对话本身。
4. **注入文本里明确写「不相关就忽略，不要硬套」**，并标注 `[笔记#2]` 这类类型与 id，
   模型需要全文时可直接 `get_note`。

**透明度**：响应里的 `retrieved` 字段回报本轮参考了哪几条，界面显示「参考了你的记录 · <标题>」。
这一条不落库，所以**刷新后该提示不再出现**（事件日志里没有它）。

## 4. 压缩（compaction）

**目的**：老内容被"浓缩"而不是被"删除"。

| 环节 | 做法 |
| --- | --- |
| 触发 | 已滑出投影窗口、且**尚未被摘要覆盖**的事件，攒够 `COMPACT_MIN_EVENTS`(8) 条才压 |
| 水位线 | 最新 `summary` 事件的 `id` 表示"已概括到哪"，只处理它之后的事件 |
| 合并 | 新摘要 = 老摘要 + 新增片段，**累积合并**成一条（prompt 里明确要求"合并成一段，不要重复"） |
| 三层保护 | ① 预算不足 → 跳过 ② 模型失败/返回空 → 退化为逐条摘录（只截取，不发明） ③ **无论如何都写一条 summary**，否则下轮会重复触发、永远卡在同一段历史 |

**迟滞的代价（诚实记录）**：因为设了"攒够 8 条才压"，那 8 条在攒够之前仍然是看不到的。
不设迟滞的话，一旦总轮数超过窗口就会**每轮触发一次摘要调用**（每次多一次模型往返，明显拖慢回答）。
这是"成本 vs 完整性"的取舍，不是 bug；要更完整就调大 `PROJECTION_ROUNDS`（窗口）而不是调小迟滞。

## 4.5 输出上限与"截断可见"（2026-09-29 补）

**问题**：回答在句子中间断掉，用户完全不知道原因。实测被问过一次"是不是达到最大字数了" ——
当时**库里查不到任何证据**：`finish_reason` 只用来打一行日志（日志一滚就没了），
`agent_event.tokens` 列一直是 NULL。事后只能把那条回答导出来、用 DeepSeek 分词器数字数倒推。

**机制（实测确认，容易踩）**：**思考（thinking）的 token 与正文共享 `max_tokens`**。
用 `max_tokens=400` 直接打 API 验证：`completion_tokens=399`、`reasoning_tokens=399`、**正文 0 字**
—— 400 个 token 全被思考吃掉了。所以"正文没写多少却撞上限"通常是思考在吃预算，
而不是正文太长（那次 16384 上限的回答：正文 13724 token + 思考约 2660 token = 正好 16384）。

**现在怎么做**：

| 环节 | 做法 |
| --- | --- |
| 返回值 | `DeepSeekClient.chatFull()` 把 `finish_reason` 与 `usage`（含 `reasoning_tokens`）带回调用方；`chat()` 仍是它的薄封装 |
| 对用户 | `finish_reason=length` 时在回答末尾附一句：输出多少 token、其中思考占多少、可以说「继续」；
思考吃光预算时直接点明"正文还没开始写" |
| 对接口 | `AiChatVO.truncated / finishReason / completionTokens / reasoningTokens`（机器可读，界面可做徽标） |
| 对排查 | `agent_event` 新增 `finish_reason` 列并写入 `tokens` —— `SELECT id, tokens, finish_reason FROM agent_event WHERE finish_reason='length'` 一条 SQL 列出所有被截断的回答 |
| 默认预算 | `ai.max_tokens` 16384 → **32768**：长文任务（"整理一份讲义"）实测需要 ~16400，原值刚好卡死 |

**为什么默认值不是"越大越好"**：只按实际生成付费，调大不额外花钱；但一次吐三万字既慢又难读，
真正的长文场景更适合**分段产出并落到笔记里**（见下）。

### 4.6 长文写进**一篇**笔记：`write_long_note`

**用户的问题**：想要一篇文章（讲义/综述）完整落进**一篇**笔记，但单次输出受 `max_tokens` 限制，
按"再点一次继续"或"create_note 一次写全文"都会在半句处断掉；
`append_to_note` 虽然能分次追加，但每次都要用户确认一下（8 节 = 8 张卡片）。

**做法**：把"分段"收进**一次工具调用**——`write_long_note(title, outline, category_name?)`：

```
大纲（每行一节）→ 逐节生成（每节一次独立调用，思考关闭、上限 2500 token）
                → 拼成一篇 Markdown → 挂**一张** create_note 待确认卡片
```

| 关键点 | 为什么 |
| --- | --- |
| 每节独立调用、显式小上限 | 单节永远撞不到全局上限；某一节写爆了还会**自动重写一次**（要求压缩到 2000 字内） |
| 每节都带"全文大纲 + 已完成小节名" | 避免各节重复与跑题 —— 分段生成最容易出的问题就是这个 |
| 只在最后挂一张卡片 | 复用 `create_note` 的审批与执行路径：用户点**一次**就成一篇，写操作仍然过确认闸门 |
| 进度用 events 回报 | "✍️ 已写 3/8 节（累计 1.2 万字）"，不是几分钟静默 |
| 单节失败不连坐 | 该节写占位提示"可以让我重写「X」"，其余照常 |
| 大纲没结构时多花一次廉价调用 | 让模型先拆小节（`expandOutline`），拆不动才退化成"整篇一节" |

**实测**（大纲 4 节，模型自行扩到 12 节）：
113 秒生成 **12 节 / 32162 字**，落进**一篇**笔记（`note#52`），全程只有**一张**确认卡片，
进度事件逐节可见 —— 而单次调用在 16384 token 上限下只能写到约 1.4 万字且必然截断。

## 5. 记忆的三层（对照 DSH 之类 agent runtime 的分层）

| 层 | 本项目的实现 | 对应 DSH 的机制 |
| --- | --- | --- |
| 长期指令 | `app_setting.ai.chat_prompt`（界面可编辑、即时生效） | `dsh-agent-instructions` |
| 会话 | `agent_event` 事件流 + 投影 | `dsh-session` + persistence + projection |
| 会话内压缩 | `summary` 事件（累积合并） | `dsh-compaction-basic` |
| 大结果外溢 | ❌ 未做（工具结果不进投影，所以暂时不需要） | `dsh-spill` / `output-retention` |

**没有抄的**：子代理、workflow、goal rounds、后台 jobs —— 对"个人笔记助手"是过度设计。

## 6. 调试与验证

| 想看什么 | 怎么看 |
| --- | --- |
| 检索命中情况 | 后端日志：`自动检索：词 N 个，命中 M 条，注入 K 条，顶部命中=…` |
| 本轮参考了哪几条 | 接口响应里的 `retrieved` 字段（比翻日志可靠，也是界面的数据源） |
| 压缩是否发生 | 日志 `上下文压缩完成：合并 N 条事件，摘要 M 字`；或直接查 `agent_event` 里 `role='summary'` |
| 会话内容 | `GET /api/ai/sessions/{id}`；或直接查两张表 |
| 阈值在哪 | `AgentSessionService.PROJECTION_ROUNDS`(8) / `COMPACT_MIN_EVENTS`(8) |

**验证压缩的技巧**（真阈值要 24 条消息才触发，成本高）：临时把这两个常量改成 `1` / `2`，
重建后端后跑 4 轮 —— 第 1 轮埋一个事实，第 3 轮会生成 summary，第 4 轮问"我最开始说了什么"，
能答对就说明摘要生效（此时窗口只有 1 轮，事实不可能来自原始历史）。
**测完务必改回并重建**，并用 `javap -constants` 反编译交付的 jar 确认常量是真值 —— 否则会把测试构建交出去。

**验证写操作拦截**（安全性验证，必须查库而不是看模型自述）：

```bash
# 1) 让模型明确调写工具
curl -s -X POST http://localhost:18080/api/ai/chat -H 'Content-Type: application/json' \
  -d '{"message":"用 create_quick_ref 工具存一条速查卡：标题「AQS 核心机制」，内容「state + CLH 队列」。直接调用工具存。"}'
# 2) 断言：pendingActions 有 1 项；库里 quick_ref 数量不变（关键！）
# 3) 批准 → 数量 +1、status=approved、事件出现「⚡ 已创建…」
curl -s -X POST http://localhost:18080/api/ai/actions/{id}/approve
# 4) 再来一次并拒绝 → 数量不变、status=rejected、事件出现「已取消：…」
curl -s -X POST http://localhost:18080/api/ai/actions/{id}/reject
# 5) 重复批准同一个 id → 必须报「该操作已处理过（approved），不能重复执行」
```

**一个必须知道的行为**：同一个会话里，对同一件事**再问一次**，模型往往不再重复调写工具
（它已经暂存过一次，会转而解释/追问）—— 想复现拦截路径请**开新会话**。
另外模型有时对"记住这件事"类请求只做检索、不做写入，这属于正常判断，不是缺陷。

## 6.5 写操作的确认闸门（write approval）

记忆层解决"模型知道什么"，这一层解决"模型能改什么"。设计动机来自一次实测：
只说了一句「记住一件事：我叫小明，正在学 Java 并发」，模型就直接建了笔记 + 分类 —— 对个人知识库来说，
**未经同意就落库是不可接受的副作用**。

| 环节 | 行为 |
| --- | --- |
| 工具分类 | `WRITE_TOOLS`（建/改笔记、建速查卡、建分类）需确认；只读工具（查笔记、`search_knowledge`）直接执行 |
| 命中写工具 | **不执行**，改为往 `agent_pending_action` 写一行 `status='pending'`（含 `tool_name` / `args_json` / `summary`），并向事件流追加「待确认：…」 |
| 模型看到什么 | 工具结果为 `{"ok":false,"pending":true,...}` 之类的"待用户确认"结果，因此模型的回答不会谎称已完成 |
| 用户批准 | `dispatch(tool_name, args_json)` **按暂存参数原样执行**（不用当前对话重算 —— 保证执行的就是用户看到的那一份），更新 `status='approved'`，追加「⚡ 已创建…」事件 |
| 用户取消 | 只把 `status` 改成 `rejected` 并追加「已取消：…」事件，**数据库零改动** |
| 幂等 | `requirePending()` 只接受 `pending` 行：重复批准/取消直接抛错，连点不会造成重复写入 |
| 失败 | 执行抛异常时把结果记为 `{"ok":false,...}`，`hint` 写成「执行失败：…」，**不能让会话日志显示成"已执行"** |

**参数快照 vs 重算**：这里刻意选择"快照"。若批准时用当前对话重算参数，用户看到的那份内容与实际写入的可能不一致。

**待确认列表要持久化**：`GET /api/ai/sessions/{id}` 会一并返回未处理的 `pendingActions`，
前端刷新后才能把它们恢复成可点的卡片 —— 否则库里那行还是 `pending`，界面上却永远点不到了。

**前端即时反馈**：点「确认执行」后，除了后端追加事件，前端还会把同一条 `hint` 挂到最近一条回答的事件角标上，
这样不用刷新就能看到「⚡ 已创建…」，且与刷新后由 `loadSession()` 恢复的表现完全一致。

## 7. 不做的事（以及为什么）

- **不做向量检索**：要引入 embedding 服务、索引与额外 token 成本，个人库规模下收益不成比例。
- **不做多会话列表 UI**：目前一个前端会话（localStorage 一个 id）+「新对话」按钮已够用；
  旧会话仍留在库里，需要时可以再加列表页。
- **不做多用户隔离**：本应用是**单用户本机工具**（后端只监听本机），没有账号体系；
  若哪天要对外提供服务，`agent_session` 需要加 `user_id` 并把接口按用户过滤。
- **不把压缩提示词做成可配置项**：对话/润色/格式三条提示词是**用户口径**，该可配置；
  压缩是内部机制（怎么把历史压短），暴露出去只会增加误解面。
