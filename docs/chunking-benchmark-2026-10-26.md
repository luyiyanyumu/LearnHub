# 结构保护与可选语义分块检索对比

结论：这次改动已解决合成样例中的代码块被拆散问题，但没有证明首位召回率全面提高。语义分块让一题在固定上下文预算内收齐证据，代价是构建耗时约翻倍；17 道长资料题未观察到额外召回收益。因此建议默认启用结构保护，长资料语义分块保留为可选项，默认关闭。

## 试验条件

- 10 篇手工编写的合成中文软件学习资料，总计 19,810 字符；31 个问题均标注原文答案证据跨度。涵盖无标题多主题长文、Markdown 标题、跨空行 Java/Bash 代码、多行 LaTeX、Markdown 表格与短速查卡。所有标题统一使用合成资料编号，不依据标题或文件名判定命中。
- 三组实际调用 Java 实现。旧版是改动前 Git HEAD 的 `TextChunker.java` 快照；结构组为新 `TextChunker.java`；语义组为新 `TextChunker.java` 与产品使用的 `SemanticChunker.java`。没有在 Python 中仿写分块算法。
- 全部使用本机 Ollama `qwen3-embedding:4b`，输出 2560 维，同样的标题上下文前缀、原始查询、余弦排序与单并发请求，批量为 4。没有云模型、重排器或回答生成。
- 目标 800、重叠 120、上限 1200 字符；语义断点百分位固定为 85，只对 `file` 且正文不少于 4000 字符的 A/B/F 三篇资料启用。这三篇分别为 5111、5193、4181 字符。
- 固定 2400 字符正文上下文预算，按向量排序遍历前 10 个候选，整块放入。剩余预算不足时跳过该块并记录，不截坏代码或公式。每题均有候选因剩余预算不足而跳过；这不代表每题检索失败。
- 正文证据命中要求覆盖答案证据至少 20% 且不少于 24 个非空白字符；完整覆盖要求所有标注跨度全部出现。多段证据可以由多个取回块共同覆盖。指标的精确定义与评分校验见工具 README 和 `test_metrics.py`。

## 结果

| 指标 | 改前规则切割 | 结构保护 | 结构保护 + 可选语义 |
| --- | ---: | ---: | ---: |
| 块数 | 38 | 38 | 40 |
| 正文证据 Hit@1 | 29/31（93.55%） | 28/31（90.32%） | 28/31（90.32%） |
| 正文证据 Hit@3 | 31/31 | 31/31 | 31/31 |
| 预算内至少命中一部分证据 | 31/31 | 31/31 | 31/31 |
| 预算内完整证据覆盖 | 30/31（96.77%） | 30/31（96.77%） | 31/31（100%） |
| 平均证据字符覆盖率 | 98.77% | 98.77% | 100% |
| MRR | 0.96774 | 0.94624 | 0.94624 |
| 保护结构破坏数 / 标注结构数 | 1/4 | 0/4 | 0/4 |
| 构建耗时，含嵌入 | 6.233 秒 | 6.237 秒 | 12.696 秒 |
| 其中边界嵌入 | 无 | 无 | 105 个向量，6.608 秒 |
| 本地余弦排序耗时 P50 | 0.260 毫秒 | 0.285 毫秒 | 0.269 毫秒 |
| 批量查询嵌入摊销均值 + 排序均值 | 45.531 毫秒 | 45.587 毫秒 | 45.535 毫秒 |

4 个保护结构分别为 812 字符的多行公式、982/263 字符的代码围栏与 766 字符的表格，均小于块上限。旧版破坏了其中较长的 Java 代码块，新版完整保存了 4 个结构。该统计只证明这些样例，不代表所有任意复杂或超长结构均无损。

第一次加载与预热实测 45.909 秒，单列且不计入稳态构建时间。三组各自实际嵌入索引块，构建时间包含 Java 分块与网络请求；语义组还包含单元边界嵌入。没有做多轮计时，因此不能把约 0.01 秒的组间差异解读为性能优势。

三组复用同一组查询向量以固定检索输入。31 个查询的批量嵌入总计 1.403 秒、摊销为每题 45.267 毫秒；这不是线上单次请求 P50，也不包括混合召回、相邻补全、重排和答案生成。可选语义分块在入库时执行，查询阶段不应重新计算这些边界。

## 逐题变化说明

- q13 要求结合完整损失式解释温度参数。旧版首块带有较多公式尾部，新版把解释和公式结构保留在不同块中。按本实验以全部证据字符计的命中阈值，首个达到阈值的块从第 1 位降到第 2 位，但三组在预算内均收齐公式和解释。这说明结构完整与首位字符覆盖指标并不总是同步改善，不能据此声称答案一定退化或提升。
- q21 同时要求限流退避方法及写请求幂等条件。旧版与结构组均取到约 61.98% 的标注证据；语义组取回完整表格行与解释。表格资料 E 本身未启用语义切割，改善来自其他长文块变短后全库候选竞争与预算占用变化，不能将这题解释为“语义分块改善了表格切割”。
- q26 询问令牌日志脱敏与异常路径。三组相关证据都从第 2 位出现，预算内均完整覆盖；改变分块没有解决这个首位排序问题。
- 17 道长资料问题在三组中均为 Hit@1 16/17、Hit@3 17/17、完整覆盖 17/17。这个目标子集没有显示语义切割新增收益。短速查 4/4、代码 3/3 问题在三组都完整覆盖。

## 适用范围与后续选择

这是固定模型下的纯向量召回对比，用于隔离分块影响。项目实际还有混合召回、相邻块补全与重排；本实验没有度量端到端答案正确性，也没有用线上私有资料或调用云 LLM。31 题样本较小、只有 4 个标注保护结构，不能据此推断真实知识库有稳定的百分点提升。

结构保护提供的是直接可验证的内容完整性收益，可以默认使用。当前数据不足以支持把语义切割默认打开；需要针对真实使用问题制作经授权、去敏的证据标注集后再验证，尤其关注超长扫描 PDF、标题缺失和多主题连续转写资料。

## 最终容器优先级修复确认

最终代码修正了一个独立结构问题：代码围栏之后先识别 HTML/Markdown 表格，再识别数学块，避免表头或 HTML 起始行含 `$$` 时误把表格当成公式。该修复没有修改语义模型、百分位或其他评测参数。

随后使用同一冻结题库重新 `javac` 编译并导出实际 Java 输出：结构单元与修复前原始测量所用的已编译类逐项相同；旧版、结构保护及可选语义三组的全部块正文、标题归属和序号均与原始导出完全一致。复用相同文本对应的已有向量重新计算后，31 题逐题证据覆盖、排序分数、取回内容及全部召回指标保持一致，未新增模型调用。

原始测量的构建时间、查询时间与源码 SHA-256 仍保留在 `report.json`，没有被缓存复核耗时替代。最终确认记录单独保存于 [final-validation.json](chunking-benchmark-2026-10-26/final-validation.json)，明确区分原始测量和最终代码：
