# 知识库、知识图谱与 LLM Wiki 实用性评估

评估日期：2026-10-02。依据本地运行中的 API、页面、源码及已保存的评测记录。结论适用于当前个人技术学习资料库。

**知识库检索值得保留并优先完善；知识图谱适合作为可核对的关系导航；LLM Wiki 应围绕主题整理、学习目录与补缺任务改进。当前证据不能证明图谱、Wiki 的自动注入提高了回答质量。**

这次完成了源码检查、数据盘点、页面检查和三次检索/注入探针。未新跑完整答案评测，未重建索引、生成 Wiki、修改业务数据或切换设置。历史实验结果与这次实时检查分别列出。

| 功能 | 当前价值 | 主要限制 | 建议定位 |
| --- | --- | --- | --- |
| 知识库 | 找回笔记、速查卡、PDF 中的内容，为回答提供自己的资料 | 页面搜索仍是整句词面匹配；检索命中不等于答案正确 | 主入口：统一搜索、命中段落、出处跳转 |
| 知识图谱 | 查看概念间关系、连接相关资料 | 已有错误关系被注入并参与推导；缺少答案层面的收益证据 | 辅助入口：经确认的关系、易混对比、学习前置关系 |
| LLM Wiki | 把材料整理成可读主题页，展示目录和待补清单 | 引用校验、索引范围、过期判断和主题匹配都有实现问题 | 学习整理层：主题页、可靠出处、可执行补缺任务 |

## 一、知识库：有用，但页面入口没有用足已有能力

实时 `/api/kb/status` 显示：21 个知识来源，1,518 个索引块，966,671 个索引字符；嵌入模型为 `bge-m3`。索引时间为 2026-09-30 17:49:29，接口显示未过期。

`/api/kb/vector/status` 显示：配置为 Milvus，当前生效为 MySQL；Milvus 不可达，系统自动回退到 MySQL 全扫描。检索仍能运行。这里应显示“实际生效后端”和降级原因，不能只展示配置值。当前规模是否需要 Milvus，应根据延迟与维护成本决定。

保存的 2026-09-29、97 题、top 5 对照记录中，使用 `deepseek-flash` 重排的一轮结果为：

| 路径 | 来源命中率 | MRR |
| --- | --- | --- |
| 词面检索 | 68.0% | 未在这一记录中单独记录 |
| 向量检索 | 86.6% | 未在这一记录中单独记录 |
| 融合与 LLM 重排 | 93.8% | 0.902 |

这是有价值的历史信号，说明融合检索比单一路径更容易找回标注来源。但它是“前五个结果是否包含任一预期来源”的命中率，**不是回答准确率，也不是正确段落的命中率**。语料后来发生变化，不能把它当成当前全量评测结果。旧文档中的 97.6% 来自更早的 85 题集合，不能与这轮直接混用。

评测集还存在偏重：97 题中，48 题的可接受来源含 `note:5`；跨来源用例也只要命中任意一个可接受来源即算成功。这样可能找到了那篇长笔记，却没有找到答案所在的小节。59 题有 `expectWords`，但目前检索评测并不生成答案、也不评分这些答案关键点。

这次实时探针：

- 搜索 `StringBuilder`，页面词面 API 返回 2 条结果。
- 搜索“大量字符串拼接用哪个类性能更好”，页面词面 API 返回 0 条。
- 同一句问题的向量探针找到了 `String / StringBuilder / StringBuffer 区别` 速查卡，但排在第 4 个块；前三个块来自 Milvus、Agent 等资料。说明语义检索可以找回内容，同时仍有相关性噪声。此探针未经过聊天的融合与重排，不能据此判断最终答案好坏。

原因在代码上很明确：`Knowledge.vue` 的 `doSearch()` 调用 `KnowledgeService.search()`，笔记检索把整段输入交给 SQL LIKE；聊天的融合检索走另一条路径。语义能力目前主要服务智能体和“检索体检”，没有直接成为知识库搜索的正常体验。

建议先把统一搜索做实：默认融合检索，支持来源、主题筛选；每条结果展示实际命中段落、所属标题和跳回原文的位置。用户找到一条有用内容应当比理解索引或图谱更容易。

## 二、知识图谱：能导航，现阶段不宜把所有边当事实

实时文档图有 33 个节点、34 条边，其中语义关联 9 条。概念图有 135 个节点、194 条边，其中模型抽取 132 条、规则推导 62 条。135 个概念中只有 11 个有 Wiki 跳转，别名不为空的节点只有 2 个。图谱与 Wiki 的实体身份还没有充分统一。

发现的具体错误不是显示问题，而是语义问题。边 67 记录：

> Spring -属于→ JVM

其证据原话是“Spring 是基于 Java 的，自然依赖于 JVM”。依赖运行环境不能等同于组成部分。边 169 又把同类证据记录为 `Spring -属于→ Java`。

实时提问“Spring 和 JVM 是什么关系”的图谱探针，把上述两条排在第 1、第 2；还列出了 **`Spring -属于→ JRE（推导）`**。可见错误抽取已经进入自动注入，并通过传递规则形成新的错误关系。

132 条抽取边中有 9 条没有证据句。另有 62 条推导边不直接保存原始来源，部分可以通过 `derivedFrom` 追溯；不能把“没有直接来源”一概算成错误，但展示与注入时必须清楚区分。抽取器发现证据不在素材中时只是清空证据，仍接受三元组，并统一赋予 0.9 的权重。这个权重没有表示经过校准的事实可信度。

项目已有文档记载的 12 题 Wiki+图谱联合开关实验：关闭时关键短语命中 46/48，开启首轮 45/48；10 题无差异、1 题改善、1 题退步。它是小样本联合实验，不能分别归因给图谱或 Wiki，也不能说明它们完全无用。第二轮出现答案截断，39/48 不应作为稳定性能结论。这次没有重新生成答案复测。

建议：

1. 引入待审核/已确认状态；没有可定位证据的抽取边不进入自动回答。规则推导只从已确认的边出发，保留推导链。
2. 分清“组成”“依赖”“前置知识”：新增清晰的依赖关系或拒绝无法准确归类的边；校验方向。先修复现有错误边及其推导结果。
3. 统一概念 ID 与别名，让 Wiki 和图谱引用同一个概念。MQTT 与 MQTT协议可作为同一概念的别名候选；IoC 与 DI 是相关概念，Maven 与 Maven 坐标是工具与子主题，不能一律合并。
4. 把常用体验做成“这个概念关联哪些原文”“A 与 B 有什么区别”“学习它需要哪些前置知识”。当前只有 1 条 `prerequisite` 边，尚不足以形成可靠的学习路线，需要补充并确认前置关系。

[Microsoft GraphRAG 的查询说明](https://microsoft.github.io/graphrag/query/overview/)区分针对实体的局部查询与面向全库的主题查询，并把原文块与结构数据结合使用。据此及本项目实测，我建议按问题场景选择图谱，而不将图谱当成所有问题的必选上下文。

## 三、LLM Wiki：有整理价值，基础可信度需要先修复

可见主题共 48 个，其中已生成页面 38 个，包含 32 个实体页；12 个已生成页有 `quality=warn`。UI 却直接把 `topics.length` 写成“48 页编译产物”，其中包括未生成主题。注入探针按数据库统计为 39 页，与可见已生成页数量也不同，需核对遗留页并统一计数口径。

以下问题均有当前代码或实时结果支撑：

| 问题 | 实际证据 | 影响 |
| --- | --- | --- |
| 真实速查卡引用被误判 | 实体编译保存 `quick_ref-3` 等合法编号；`WikiQuality` 把 `[速查卡#3]` 转为 `ref-3` 后校验 | `@GetMapping`、dsh、git 等页出现“引用不存在”告警，真实标记被去掉括号，失去出处链接 |
| 索引只列最近一批 | 实体页保留历史页面，但调用 `upsertIndexPage(chosen)`，`chosen` 最多 10 个 | 当前 32 个实体页，知识索引只收录 10 个，却宣称不会漏项 |
| 编译页过期状态不可靠 | 实体/索引/自检页的 `stale` 固定为 `false`；实体 hash 是类型加批次计数 | 无法按原文变化可靠提示待更新；自检报告仍停在 9 月 21 日 |
| 自动更新覆盖范围有限 | `onKnowledgeChanged()` 只按分类 ID 调度分类页 | 页面上“改完笔记自动重生成”容易让人误以为标签、实体页也都会更新 |
| 来源计数误导 | 27 个实体页显示计数为 1；该数实际上按每批抽取命中累计，4 份素材一批 | 不能解释为独立素材数，应改为去重后的来源集合大小 |
| 特定主题检索被通用页抢占 | 问“关于 MQTT，我的知识库里还缺哪些关键点？”时，实际注入知识索引、知识自检两页 | MQTT 页已经有 QoS、Broker、Topic 的待补清单，却未注入 |

“素材覆盖率”也需要准确解释：当前 Java 页接口显示 2%，AI Agent 标签页显示 4%，这是当前字符采样占源文长度的比例，不是知识完整度。页面生成时保存的正文与现在重新计算的素材覆盖率可能不属于同一个快照，过期页面尤其需要标注。

此外，实体编译先把每份源文本截到 14,400 字，再从其中采样 2,400 字；长 PDF 的后半部分并没有进入实体抽取。均匀采样的注释容易让人以为整本资料已经被覆盖。

Wiki 的“待补充”目前混合了三种情况：原库确实没有材料、材料有但本次采样没送到、生成页没有展开。注入提示却要求模型明确说“你的知识库里没有记这一点”。例如 AI Agent 页把采样缺失章节列为待补充，不能因此认定原笔记也缺失这些章节。应先查原文索引，再把缺口标为“全库未找到”“采样未覆盖”或“页面未展开”。

现有校验主要检查来源编号、章节与长度，不逐句验证事实。因此“已校验”更适合写成“格式与引用编号通过”；对于有证据支持的事实，需进一步验证引用是否真的支持相应论断。

建议把 Wiki 页做成可维护的学习卡片：概念说明、自己的原文出处、已确认的关联、待补任务、最近核对时间。让用户能从一个缺口直接跳到相关原文或补写笔记，而不是重复生成越来越多近似摘要。

## 四、建议实施顺序与验收条件

以下是改进方案，这次评估没有实施业务变更。

| 优先级 | 改动 | 可核对的验收条件 |
| --- | --- | --- |
| P0 | 统一 `note / quick_ref / file` 来源编号，修复真实引用被剥除的问题 | 已存在的速查卡引用校验通过并可跳回原文；无效 ID 仍能识别。优先用原始生成文本重新校验，无法恢复时只重生成受影响页 |
| P0 | 从全部已存实体生成知识索引；区分主题数、已生成数 | 当前索引覆盖 32 个已有实体；新增、删除后数量和链接一致 |
| P0 | 修复 Wiki 主题匹配与缺口语义 | MQTT 问句命中 MQTT 规范页；通用“知识库”字样不能压掉明确主题；采样缺失不得被说成全库缺失 |
| P0 | 隔离图谱未确认边，修正错误方向及派生关系 | Spring/JVM 探针不再输出“Spring 属于 JVM/JRE”；每条注入边可追溯到支持它的段落 |
| P1 | 知识库主搜索使用融合检索，提供段落与位置跳转 | 口语改写可找回资料；结果能直接定位证据；来源类型筛选行为清楚 |
| P1 | 为 Wiki、图谱保存来源 ID、内容指纹与依赖映射 | 修改/删除来源后，相关分类、标签、实体页和边准确标脏；无关页不重生成 |
| P1 | 统一概念身份、别名与 Wiki 链接，整理近重复主题 | 同一概念只有一个规范入口；相关但不同的概念保留关系；旧链接仍可解析 |
| P1 | 增加答案级评测与实际使用记录 | 可判断图谱/Wiki 是否提高正确性、出处质量、找资料速度，且能量化延迟与生成成本 |

答案级评测建议保留现有 97 题作回归，同时增加 30 条人工标注题：关系题 10、跨资料综合题 10、库内缺口/无答案题 10。跨来源题要求覆盖所有必要证据，不能仅命中任一文件即成功；每题标注正确段落、关键事实和应引用的来源。

对同一冻结语料和同一模型，分别跑基础检索、基础检索+Wiki、基础检索+图谱、三者组合四组；同题多次运行，人工核对差异并报告波动。记录事实正确性、引用支持与完整性、无答案处理、耗时、token 和成本。检索层还要报告按来源与题型拆分的表现，避免一篇长笔记主导总分。

这种评估区分检索与答案质量，符合 [ALCE 论文](https://aclanthology.org/2023.emnlp-main.398/)将答案正确性、引用质量等分开测量的思路。收益门槛需要在实验前约定，例如关系题确有重复稳定的改善、普通题没有明显退步、额外延迟可接受；没有增量收益的自动注入可关闭，保留页面导航。

产品使用指标可以很轻：匿名于本地记录检索是否点击原文、一次查找耗时、用户是否标记“有用”、补缺任务是否完成。热力图可以记录学习行为，但编辑次数本身不能证明检索、图谱或 Wiki 有帮助。

## 五、主要代码证据

- `frontend/src/views/Knowledge.vue`：默认进入图谱；`doSearch` 为词面 API；第 765 行将批次计数标为来源证据，第 1078 行将主题总数标为编译页数。
- `backend/src/main/java/org/dyh/learnhub/service/KnowledgeService.java`：第 53 行起统一词面搜索；`NoteService.java:66` 使用整段输入 LIKE。
- `backend/src/main/java/org/dyh/learnhub/service/RagEvalService.java`：第 80 行起按来源命中评分，不评价生成答案。
- `backend/src/main/java/org/dyh/learnhub/service/EntityCompileService.java`：第 312 行只给本批候选建立索引；第 348 行起截断后采样；第 426 行生成 `quick_ref-*`；第 463 行按批次累加；第 510 行保存弱指纹。
- `backend/src/main/java/org/dyh/learnhub/service/WikiQuality.java`：来源类型归一化为 `ref`；校验编号、结构、长度，未做逐句事实核对。
- `backend/src/main/java/org/dyh/learnhub/service/WikiService.java`：第 201、263 行固定编译页过期状态；第 865 行起按关键词匹配注入；第 1125 行起只按分类调度更新。
- `backend/src/main/java/org/dyh/learnhub/service/TripleExtractor.java`：第 145 行不匹配证据被清空，三元组仍可接受；第 154 行统一权重 0.9。
- `backend/src/main/java/org/dyh/learnhub/ai/AgentService.java`：第 712 行起共用 7,000 字注入预算；第 757 行起上报候选参考来源；第 941 行起事后核对答案证据。上报来源未按预算实际保留的条目重新筛选，应统一候选、实际注入、工具读取、最终引用的口径。
- `frontend/src/components/AgentPanel.vue`：读取并展示 `retrieved` 标题，目前没有消费/展示后端 `grounding` 结果。
- `docs/rag-design.md`：第 139 行起记载联合注入对照实验，第 196 行起记载 Wiki 目录/缺口实验。这里的历史实验不足以替代当前语料的新评测。

当前最值得投入的是可靠的检索和出处，其次是统一来源与概念的数据基础，再让图谱和 Wiki 服务明确的学习任务。暂时没有证据支持通过增加图谱规模、扩大 Wiki 自动生成量或更换数据库来解决上述质量问题。
