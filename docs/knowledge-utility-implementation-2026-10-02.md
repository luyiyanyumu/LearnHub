## 一、P0 四项：已完成，并有运行时验收

### P0-① 统一 `note / quick_ref / file` 来源编号 —— 提交 `aaca1f2`

**根因**：来源类型在代码里有**两套命名** —— `KbChunk` / `EntityCompileService` 用
`quick_ref`，而 `KgService` / `WikiService` 用 `ref`。`WikiQuality.normalizeKind`
把「速查卡」归一成 `ref`，拿 `ref-3` 去比 `idsOf()` 产出的 `quick_ref-3`，**永远不匹配**
→ 真实引用被判"不存在"、方括号被剥掉降级成纯文本（@GetMapping、dsh、git 等页）。

**修法**：`WikiQuality` 改为两种写法都认（`normalizeKind` 用规范写法 `quick_ref`，
新增 `altRef()` 做 `ref-N ↔ quick_ref-N` 互换，`kindLabel` 同时接受两者）。

**历史数据**：已按报告建议"用原始生成文本重新校验"修复 —— 先备份
（`backend/wiki-page-backup-20261002.tsv`），再 `REGEXP_REPLACE` **只重挂真实存在**的编号
`(2|3|7|8)`，命中 8 行；引 `速查卡#5`（不存在）的 2 页**未动**，无效 ID 仍被正确识别。

**验收**：
```powershell
$p = (Invoke-RestMethod http://127.0.0.1:18080/api/wiki/pages/entity-51a81e9bc1).data
$p.quality            # ok（修复前 warn）
$p.contentMd -match '\[速查卡#3\]'   # True（修复前为无方括号的 速查卡#3）
```
实体页 `quality=warn` 数量：**12 → 4**（剩余 4 页是真问题：幻觉编号 / 无有效引用）。

### P0-② 索引收录库里全部实体页 —— 提交 `ca12603`

**根因**：实体页只增不删（设计如此），库里累积；而 `upsertIndexPage(chosen)` 的
`chosen` 被 `MAX_ENTITY_PAGES=10` 截断 → 实测 32 个实体页只列 10 个，页脚还承诺
"所以不会漏项"。

**修法**：改为先查 `wiki_page` 里全部 `topic_type='entity'` 的页；本批重编的按 kind 分组列出
（保留 brief），本次未重编的历史页单列「## 其他实体页」一节；首行 / `itemCount` /
`sourceHash` 一律用库内总数；页脚不再作绝对承诺；`chosen` 为空的提前返回分支也刷新索引。

**验收**：
```powershell

$idx = (Invoke-RestMethod http://127.0.0.1:18080/api/wiki/pages/index).data
"实体页=" + ($t | ? topicType -eq entity).Count + "  索引 itemCount=" + $idx.itemCount
# 修复前：32 / 10；修复后：36 / 35（35 那次编译后实体页又增 1，索引随即标 stale，见 P1-2）
```

### P0-③ Wiki 主题匹配与缺口语义 —— 提交 `0c641c6`

**根因**：问题切词后的通用 2-gram（"知识"）同时命中《知识索引》《知识自检》的标题，
与明确主题词（MQTT）落进**同一个布尔 `titleHit` 档**；档内按 raw score 排，
再加上 `RAG_MAX_PAGES=2`，MQTT 页被截掉。另：`## 待补充` 被注入层一律说成
"素材里明确没记"，其实多半是**采样截断**造成的。

**修法**：标题命中从布尔改成**具体度** `titleScore`（ASCII 主题词 +100，中文 2 字 +1 / ≥3 字 +10）；
注入侧与探针侧共用同一套排序；缺口拆成「该页未展开」与「采样未覆盖」两类；
删掉注入前言里"你的知识库里没有记这一点"那句。

**验收**：
```powershell

(Invoke-RestMethod "http://127.0.0.1:18080/api/wiki/probe?q=$q").data.block
```
修复前：注入《知识索引》《知识自检》；修复后：**注入《MQTT协议》《MQTT》**，
且缺口标注为「待补充（该页未展开，原文里可能有）：QoS…；Broker…；Topic…」。

### P0-④ 图谱未确认边与错误方向 —— 提交 `1aab030` `cf424a3` `4118b70`

**根因**：`TripleExtractor` 证据对不上时只清空证据**仍接受**三元组并统一给 0.9；
`KgPipelineService` 入库处又硬编码 0.9（改了抽取层也不生效）；推导与注入都不筛"无证据边"；

**存量数据清理**（已执行）：

### P1-2 来源指纹与标脏 —— 提交 `06730c9`（索引页部分）

**根因**：实体/索引/自检页的 `stale` **写死 false**，编译页永远不提示"待更新"；
索引页的 `sourceHash` 是 `"index-" + 页数`（弱指纹）。

**修法**：`EntityCompileService.indexFingerprint()` 对**实体页清单**（topicKey + 标题，
不含生成时间）做 SHA-256；`WikiService.topics()` 对索引页用它重算比对。

**验收**（含一次真实的联动）：
```powershell

$idx.stale     # True —— 实体页数从 35 变 36 后，索引立刻正确标脏
```
指纹算法独立验证：同集合不同顺序**相等**；多一页 / 改名**不相等**。

**未做**：实体页自身的来源指纹与依赖映射（需要把"这一页用了哪些来源"落库）。

## 三、运维注意（踩过的坑）

1. **重建后端的正确顺序是"先停服务，再 `mvn package`"**。运行中的进程会锁住
   `target/*.jar`，直接打包会在 `repackage` 阶段报
   `Unable to rename ... .jar to .jar.original`，并留下一个 1MB 的**瘦包**（不可运行）。
   发现后必须先停服务、重新打包。旧 jar 备份在 `target/*.jar.bak`。
2. **`GET /api/wiki/pages/{topicKey}` 对不存在的页返回 200 + `data:null`**，
   用 HTTP 状态码判断"页是否存在"会**误判**（本次就误报过一次）；
   权威判断请查 DB 或看 `data` 是否为空。建议后续让不存在时返回 404。
3. `schema.sql` 是 `spring.sql.init.mode=always` 且**没有任何 ALTER**，
   MySQL 也没有 `ADD COLUMN IF NOT EXISTS` → 直接加列会在第二次启动时报
   duplicate column 并**导致启动失败**。要加列得照 `ModelProfileMigration`
   的 `ApplicationReadyEvent` + 幂等检查模式，或复用现有可空列。
4. 本会话所有数据变更都已备份：
   `backend/wiki-page-backup-20261002.tsv`（10 个实体页）、`backend/wiki-cat0-backup.tsv`。

| --- | --- | --- | --- |

**结论：别名机制已经收敛，继续跑编译不会提升关联数。** 两个原因：
1. **模型对多数实体页不返回 `aliases`** —— 优先队列里剩下的实体（`@GetMapping`、

- 提高实体页产出（`MAX_ENTITY_PAGES` 目前 10/批，且 `chosen` 来自当轮抽取出的候选）；
- 或者放宽匹配（前缀/包含）—— 但报告明确警告 IoC 与 DI 是**相关但不同**的概念，
  模糊匹配会引入错误合并，必须配人工确认（现成工具：`GET /concept/duplicates` + `POST /concept/merge`）；
- 或者接受"只有部分概念有长文页"这个现实，把目标从"提高关联率"改成
  "让**已关联**的那部分可靠、并在 UI 上把'无页概念'与'有页概念'区分开"。

建议下一轮**不要再跑编译**，直接在上述三个方向里选一个。

### 7.2 配套改动：缺口题不能进召回率的分母

**问题**：`expect_refs='none'` 的题永远不会"命中"，`RagEvalService.run` 却把每条用例
都算进分母 —— 于是**每启用一条缺口题，recall 就白掉一分**。30 题全启用会凭空把
recall@5 从 0.939 拉到 0.783，看起来像"检索退步了"，其实是评测集口径错了。

**修法**：`isGapCase()`（认 `none`/`NONE`/`无`/`-`/空 等多种写法）把缺口题从
recall/MRR/词面/语义四个分母里全部剔除，并在响应里单独给出
`scoredCases` / `gapCases` / `gapWithHits`；缺口题"检索到东西"只作信息项
（`gapWithHits`），**不判好坏** —— 该不该说不知道是答案级的事（见 7.3）。

**验收（关键）**：改动前后对 99 题基线**无影响**，因为当前 `enabled=1` 里一条缺口题都没有：

| 指标 | 文档基线（来源去重后） | 本轮改动后复跑 | 结论 |
| --- | --- | --- | --- |
| cases / scoredCases / gapCases | 99 / — / — | 99 / 99 / 0 | 分母一致 |
| recall@5 | 0.939 | **0.939** | 完全一致 |
| keywordRecall | 0.687 | **0.687** | 完全一致 |
| vectorRecall | 0.869 | **0.869** | 完全一致 |
| MRR | 0.869 | 0.866 | 在重排波动内，见下 |

MRR 那 0.003 的差不是回归：检索链路里有**模型重排**，同一配置重复跑本来就会飘 ——
历史里同标签两次跑的 MRR 分别是 0.743 / 0.759（差 0.016），另有一组 0.759 / 0.815（差 0.056）。
**recall 与两路对照完全一致**，说明我的改动对非缺口题是逐位等价的。

| 维度 | 字段 | 定义 | 口径说明 |
| --- | --- | --- | --- |
| 答案正确性 | `answer_accuracy` | `expect_words`（人工标注关键事实）在答案里的覆盖率 | **代理指标**；覆盖率≠正确，所以逐条答案都存 detail 供人工核对。没标注的题返回 -1 **不参与均值**（把"没标注"当 0 分会把均值拖垮）|
| 引用支持 | `citation_support` | 复用 `GroundingService`：答案有没有超出注入的证据 | 没有证据/未开校验的题不入分母 |
| 引用完整性 | `citation_coverage` | 多来源题的**必要来源是否全部**进 top-k | **ALL 口径**，报告明确要求"不能仅命中任一文件即成功" |
| 无答案处理 | `no_answer_score` | **缺口题**的正确拒答率（该说不知道时说了没有）| 见 7.5②：与"有材料却拒答"分开记 |
| 耗时与成本 | `elapsed_ms` / `avg_latency_ms` / `prompt_tokens` / `completion_tokens` / `total_tokens` / `est_cost` | 墙钟耗时 + 输入/输出 token | 成本要**设置单价**（`kb.eval.price_in_per_m` / `kb.eval.price_out_per_m`），没配就是 0 —— 宁可不给，也不编一个价 |

**可复现性**：每条运行都存 `corpus_hash`（语料指纹，聚合 `kb_index_state` 的内容哈希）、
`model`、`prompt_version`（当前 `answer-eval-v1`）、`wiki_inject` / `kg_inject`。
这四个量任一变了分数就不可比 —— 不存它们，历史里的两条记录会看起来像"退步了"。

**四臂对照**（报告要求"基础 / +Wiki / +图谱 / 组合"）不需要新代码：wiki 与图谱注入
本来就有开关（`kb.wiki_inject`、`kg.inject`，**默认都开**），评测会把当时的两臂状态记进
`wiki_inject` / `kg_inject`。关掉其一再跑一轮，即可得到对应那一臂。

**证据与命中来自同一次检索**：`Retriever.evidenceFor()` 返回 `Evidence(refs, text)`。
拆成两次调用会**翻倍付出重排的模型成本**，而且重排是模型判断、不是纯函数，
两次可能给出不一致的结果。

接口（都在 `/api/kb` 下，与检索评测并列）：
```
POST /api/kb/eval/answer/run?label=&topK=5&limit=10&mode=fused&ids=126,132,139
GET  /api/kb/eval/answer/history
```
`limit` 默认 **10**：这一轮**每条都要真调一次模型**（还要跑核对），比检索评测贵得多也慢得多，
所以默认限量。`ids` 传了就**忽略 `enabled`**，用来在正式启用前先试草稿题。

### 7.5 实测抓出来的两个问题（都已修，且都留了回归测试）

**① 拒答启发式误判：noAnswerScore 0.25 → 1.0**

第一版"只要出现缺失类说法就算拒答"，结果 3 条**完全正确**的回答全被判成误拒。
原因是模型习惯在正确回答**末尾**补一句"材料未覆盖底层实现细节"（范围声明），
而"没有相关"正好命中标志词。

修法：**态度看开头** —— 强标志（"无法回答"/"没有足够"等）任意位置命中即算拒答；
缺失类说法只在**开头 200 字内**才算（实测：正确回答的范围声明在 350 字之后，
拒答的结论句都在前 40 字内，两边余量充足）。回归测试用 id=126 的**真实回答原文**锁住。

**② 一个真实发现：来源召回了 ≠ 证据到位（id=139）**

139 是跨资料题（`note:2|file:2`），`citation_coverage=1.0` —— 两个来源**都**进了 top-5。
但模型仍然老实回答"材料里没有足够内容回答这个问题"，正确性只有 0.5。
看证据就明白了：注入的是**摘要片段**（2519 字），
PDF 里"ApplicationEnvironmentPreparedEvent / addListeners"那一段根本不在片段里。

**所以"top-k 覆盖率 100%"和"模型手上有答案"是两件事。** 这正是答案级评测的价值 ——
检索级指标永远看不到这一层。短期不必改检索：把它记成 `falseRefusals` 诊断项，
提醒去查"是不是片段截得太短"。

也正因为这个发现，`falseRefusals` **没有并进 `noAnswerScore`**：
并进去会让 0.75 看起来像"模型 25% 的时间在瞎答"，而实际是两种问题各占一半。分开记才解释得清。

### 7.6 运维注意（本轮新增）

1. **新表可以直接建，新列必须走幂等迁移 —— 而且这个项目本来就有这个机制。**
   交接书里"schema.sql 没有任何 ALTER"的说法**不准确**：文件第 189 行起就是
   一段幂等迁移区（`information_schema` 查一下 + `PREPARE/EXECUTE` 动态执行），
   已有 note.summary / file_info.read_* / agent_event 等十来处先例。
   本轮给 `rag_eval_answer_run` 加 `false_refusals` 就是照这个模式做的（第 13 条迁移），
   并且**实测过**：该表先前已经建过，直接改 `CREATE TABLE IF NOT EXISTS` 不会生效，
   走迁移后重启，列出现且启动无报错。
3. **`INSERT IGNORE` + 窄列 = 静默截断（本轮真踩了）。**
   `note` 原本是 `VARCHAR(255)`，而人工标注题的 note 要装"考什么 + 依据 + 原文摘录"，
   最长 399 字。`INSERT IGNORE` 会把 `Data too long` 这个**错误降级成 warning 并截断**，
   于是 5 条（id 140/141/142/147/148）的证据摘录被拦腰砍断（尾部停在 "另一种补救是 @"），
   而**导入照样报成功**。靠"看导入有没有报错"根本发现不了。
   已把 `note` 通过幂等迁移加宽到 `VARCHAR(1000)`（schema.sql 第 14 条），并用草稿文件回填了全文。
   **通则**：灌这类长文本后必须复核长度 ——
   `SELECT MAX(CHAR_LENGTH(note)) FROM rag_eval;`，别只看导入的退出码。
4. **答案级评测很贵**：6 条约 40 秒、约 9000 token。默认 `limit=10`。
   要跑全量 30 题请显式传大 `limit`，并预期分钟级耗时与相应 token。
5. **启用 30 题之前先想清楚分母**：7.2 已让缺口题不进分母，所以启用它们
   **不会**拖低 recall@5 —— 但仍建议分批启用、每批跑一次 `POST /api/kb/eval/run` 看历史对比。
6. 本轮所有验证脚本与导出物都在 `%TEMP%\lh-materials\`（含 `reports\` 下的
   `answer-detail-final.json` 等），未提交进仓库。
