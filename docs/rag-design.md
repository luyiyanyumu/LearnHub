# 检索（RAG）的缺陷与改进：全部用指标说话

这份文档记录检索改造：**改了什么、为什么改、实测提升多少、还剩什么缺陷**。
所有数字都来自 `POST /api/kb/eval/run`（**85 条**固定用例，跑的是与线上完全同一条检索链路）。

> 用例规模从 27 扩到 85 是因为：27 条时 1 条用例 = 3.7pp，小改动根本判别不出来；
> 现在 1 条 = 1.2pp。扩充方式：38 条从真实小节标题派生（词面型）、29 条手写口语问法（语义型）、
> 9 条词面基线、9 条跨来源。派生的那批偏简单，所以**关键是那 29 条语义型** —— 它们才是区分度的来源。

---

## 0. 先立指标（不然改动只能靠感觉）

原来只有一个"检索体检"：手动拿一个问题对比词面 vs 语义的命中 —— 那是**演示，不是指标**。
现在有：

- 表 `rag_eval`：85 条用例。**问题用真实口语，不照抄标题** —— 照抄标题测的是"字符串相等"，
  真实难点是"用户这么说、资料里那么写"。
- 表 `rag_eval_run`：每次运行的 recall@5 / MRR / 两个对照组，保留历史用来对比。
- 指标口径：`recall@k` = top-k 里出现任一期望来源；`MRR` = 首个命中位置倒数的均值
  （recall 看不出"排第 1 还是第 5"，MRR 补这一刀）。
- 对照组必须**干净**：跑 `keyword` / `vector` 模式时会关掉重排与另一路。

## 1. 最终实测（85 条用例）

| 配置 | recall@5 | MRR |
| --- | --- | --- |
| 只用**词面**（干净对照） | 0.729 | — |
| 只用**语义**（干净对照） | 0.929 | — |
| **融合 + 上下文嵌入 + 重排**（线上默认） | **0.976** | 0.916 |

关键结论：**融合比词面高 24.7pp、比语义高 4.7pp** —— 用例扩到 85 条（尤其是加了 29 条口语语义型）
之后，融合的价值才真正显出来；27 条时词面能到 0.889，是因为那批用例里一半的关键词直接在标题里。

### 改动过程中留下的 A/B 轨迹（历史里可查）

| 标签 | recall@5 | MRR | 说明 |
| --- | --- | --- | --- |
| A 无上下文嵌入 | 0.963 | 0.759 | 27 条时期 |
| B 带上下文嵌入 | 0.963 | 0.815 | **上下文嵌入 +5.6pp MRR** |
| C/D +重排 | 0.963 | 0.926 | **重排 +11.1pp MRR** |
| E 修切块 + 85 条 | 0.976 | 0.921 | 换到 85 条后的新基线 |
| F 放宽召回带 | 0.976 | 0.884 | **假设被证伪，已回退** |
| G/H/I 图谱扩展 + 修来源饿死 | 0.976 | 0.916 | 见下 |

## 2. 逐条改动

### ① 切块带上下文（contextual retrieval）

`TextChunker.splitWithHeadings()` 先按 Markdown 标题分节、记住标题路径（`H1 > H2 > H3`），
节内再按长度切；嵌入时用 `TextChunker.embedText()` 把「文档标题 · 小节」前置。
`kb_chunk.heading` 单独存小节路径，`chunk_text` 仍存正文（不污染给模型看的片段）。

**A/B 实测**（关掉开关重建一次，同一组用例）：语义单路 recall 0.889 → 0.926、MRR 0.759 → 0.815。

### ② 切块器的两个真 bug（靠扩充评测集时的排查才暴露）

1. **标题里的 HTML 进了向量**：note#5（5.9 万字，本库最大来源）的标题写成
   `<font style="color:rgb(0,0,0)">一、Java核心基础</font>`，直接嵌入等于往向量里塞 `rgb(0,0,0)` 噪声。
   → `cleanHeading()` 去 HTML 标签与 Markdown 强调标记。
2. **代码围栏里的 `#` 被当成标题**：SQL/Bash 示例中的 `# 查询表中所有字段` 成了小节标题，
   把真实层级冲掉。→ 进入 ```` ``` ```` 围栏后不再解析标题。

修复后核实：**168 个块带小节，含 HTML 的 0 个、被代码注释污染的 0 个**。
单测 `TextChunkerTest` 锁住这两个坑（5 个用例）。

### ③ RRF 融合（替代"首尾相接"）

原来 `out = top(词面) + semantic(语义)`，而两套分数量纲不可比（词面是命中次数×整数权重、
语义是余弦×100），拼接会让语义最相关的永远排在词面勉强命中的后面。
现在按**名次**融合：`score = Σ 1/(60 + rank)`，双路命中的两个名次都计入。

同时把**候选池**与**每路候选数**对齐（之前不一致，等于没把池子调大）：
`VECTOR_TOP_K 4 → 16`、融合池 `6 → 24`、最终注入 8 条。

### ④ 上下文总预算

四路证据源共享 `RETRIEVAL_BUDGET_CHARS = 7000`，按序分配；条目级截断（放不下整条不写）。

### ⑤ 增量索引 + 自动触发

`kb_index_state`（`type:id` + 内容 sha256）+ `POST /api/kb/reindex`，并用**指纹对比**而不是
接收事件 id（写入路径有四条，靠事件传 id 一定漏）。

| 场景 | 结果 | 耗时 |
| --- | --- | --- |
| 内容没变（全跳过） | `reindexed: 0` | **245 ms** |
| 改一条笔记 | `reindexed: 1, chunks: 2` | **589 ms** |
| 对照：全量重建 | 381 块 | **23 s** |

另外挂上了变更事件（`kb.auto_index` 默认开）：防抖 20s、两次运行最小间隔 30s，
且真正决定"要不要嵌入"的是指纹 —— 所以"改一个字就花一次嵌入"不会发生。

### ⑥ 模型重排（默认开）

`RerankService`：召回后把候选（标题 + 120 字摘要）交给模型按"对回答这个问题的用处"重排。
**MRR 0.815 → 0.926**。候选超过 20 条时**分批 + 批间轮转**（窗口 20 → 60），
而不是一次给 60 条（提示词变长会摊薄注意力、失败时影响面也更大）。
失败返回原顺序 —— 重排挂了不能连检索结果一起没有。

### ⑦ 图谱辅助的查询扩展

把问题里识别到的概念、以及它们一跳邻域的概念名补进**检索词**，让词面那一路也能命中
（"物联网设备上报数据" → 补进 `MQTT`）。

实测：词面 recall 0.718 → **0.729**，整体 recall 持平、MRR 0.921 → 0.916（≈噪声）。
代价为零（纯图查询、不调模型），所以保留。**它的边界也很清楚**：问题里没有任何图内概念时无扩展可做（见下）。

### ⑧ 修掉"小来源被饿死"（三元组抽取的覆盖缺陷）

排查那两条召回失败时发现：**概念图里根本没有 MQTT** —— 而 MQTT 是 note#3 的全部内容。
根因是抽取按"字符分批 + 每批最多 12 条"，于是 PDF（6000 字）先把预算吃光，
109 字的 note#3 排在最后、一条都抽不到。

→ 改成**按来源抽取**：每个来源有自己的 12 条额度。调用批次几乎没变（15 vs 14），
但**覆盖不再随篇幅偏斜**：MQTT 进图（`MQTT -是一种→ 消息协议`、`MQTT -用于→ IoT 低带宽/弱网`），
实体从 86 → **121**，推导事实 31 条。

### ⑨ 答案级校验（grounding check）
检索只能保证"材料在上下文里"，不能保证"模型按材料说话"。`GroundingService` 把
（问题 / 注入的证据 / 模型答案）交给模型，列出**无法由证据支撑**的断言，结果随回答一起回报界面。

**双向验证过**（`POST /api/kb/grounding/check`，见下表）—— 一个"总是说没问题"的核对器毫无价值：

| 样本 | 期望 | 实测 |
| --- | --- | --- |
| 答案完全来自证据 | grounded | ✅ `grounded=true`，不支撑 0 条 |
| 答案编造 4 条（端口 1883 / TLS 1.3 / 报文 256MB / 规则引擎） | 不 grounded | ✅ `grounded=false`，**恰好抓出这 4 条** |

设计取舍：**只标记、不改写**（自动改写会掩盖"知识库确实没记这个"）；**没有证据时不校验**
（标"本轮无材料"比把常识回答判成幻觉更诚实）；核对失败不阻塞回答。

## 2.5 第三/四路（主题 wiki / 概念图谱）注入的 A/B：**测不出收益，但成本砍到 1/3**

这两路一直**默认注入**，却是四路证据源里唯二**不在评测集里**的（`rag_eval` 的期望来源只有
note 73 / ref 14 / file 10，`retrieveRefs` 也只覆盖融合后的笔记/速查卡/资料）。
"有没有用"因此一直只能靠感觉 —— 2026-09-29 补了开关再测。

**先加开关**（这是能测的前提）：`kb.wiki_inject` / `kg.inject`，走 `PUT /api/settings`
（键已登记进 `buildKnownKeys`，否则白名单直接 400 而界面只看到"没生效"—— 这个坑踩过一次）。
默认开 = 保持原行为；关掉只影响本轮上下文，不影响页面、自动刷新与 `graph_*` 工具。

**A/B 设计**：12 题（关系型 6 / 主题型 3 / 已知两路都漏 2 / 前置 1）× 2 组
（A=关注入 / B=关注入），同模型同 prompt、每问独立会话、切开关后各跑一轮；
评分 = 每题"用户自己记录里的 4 个关键短语"命中数（比"答案对不对"更贴目标：测的是"有没有用上你的记录"）。

| 组 | 关键短语命中 | 平均答案 |
| --- | --- | --- |
| A（关闭注入） | **46/48** | 4245 字 |
| B（注入 wiki+图谱） | **45/48**（首轮）/ 39/48（次轮） | 2888 字 |

逐题：**10 题无差异**、1 题 B 好、1 题 B 差 → 结论是**噪声级，测不出收益**。

**但次轮的 39/48 不能当结论**：那条数字来自 3 个 **253~462 字**的短答案，复测发现
同一批问题同样配置会给出 3493~7788 字（12 次复测里 0 条短答案）—— 单轮小样本会被
**偶发截断**污染，用它下结论等于拿噪声当信号。**方法论教训：这类 A/B 必须同题多轮取中位数，
不能用"跑一遍 12 题"的结果宣布结论。**

**改进（无论有没有收益都成立：这两块的问题不是"要不要留"，而是"太贵且太散"）**：

| 改动 | 前 | 后 |
| --- | --- | --- |
| 图谱：只在**关系型问题**注入（命中 ≥2 概念，或含"关系/区别/易混/先学/先掌握/属于/包含/依赖"） | 见概念就注入 | "MQTT 适合什么场景"**不注入**（省 700+ 字） |
| 图谱：块内三元组上限 | 24 条 | **6 条** |
| 图谱：对称补齐边去重（`A 易混 B` 与 `B 易混 A（推导）` 是同一件事） | 两向都注入 | 同一对只留**有证据**那条 |
| 图谱：排序按信息量（两端命中 > 有证据 > 定向关系） | 原顺序 | 关系题的第一条就是推导结论（`JVM -属于→ JDK（推导）`） |
| wiki：注入页数 | 2 页 | **1 页** |
| wiki：注入内容 | 整页截前 600 字 | **按小节打分，只注入最相关的那一段** |

实测块大小（同一批问题）：

| 块 | 改进前 | 改进后 |
| --- | --- | --- |
| 概念图谱 | 732 ~ 1281 字 | **489 ~ 583 字**（MQTT 这类常识题 = 0） |
| 主题 wiki | 600 ~ 1200 字 | **183 ~ 203 字** |

另外给 `retrieved` 里的 wiki/graph 条目加了 `chars` —— 注入成本要能被看到、能被统计。

**暴露出来的真问题（下一步该做的）**：

1. **抽取侧的方向错误会被注入放大**：`Spring -属于→ JVM`（证据原话是"Spring 是基于 Java 的，
   **依赖**于 JVM"）、`JDK -属于→ Spring Boot 启动流程`（把**文档标题**当实体）。
   这类边在关系题里排第 1/第 4，正是"注入错误关系比不注入更糟"的那类风险。
   修法在抽取侧：`part_of` 方向判据（"包含 / 依赖 / 基于"不能都折成 `part_of`）+ 禁止文档标题成为头实体。
2. **关系型问题没有评测集**：现在的 97 条期望来源里没有 `wiki`/`graph`，`retrieveRefs` 也不返回这两块
   —— 要判定它们值不值，得先补 25~30 条关系型用例并让评测入口覆盖这两块。
3. wiki 近重复主题（`MQTT` / `MQTT协议`、`DI` / `IoC 与 DI`、`Maven` / `Maven坐标三要素`、
   `Docker`(category) / `Docker`(entity)、`dsh` / `DeepSeek Harness`）会分散"该注入哪一页"。

### 2.6 wiki 改成"目录 + 缺口"后：技术问题仍无增量，元问题才有

第 2.5 节之后又做了一轮，方向是**换掉注入的内容形态**（而不是继续调分数）：
wiki 页平均只聚合 **1.9 条来源**（39 页里 29 页带「待补充」段），所以"整页/某段摘要"本质上
是原文的第三种写法。改成注入**目录 + 缺口**：主题有哪些小节、来源几条、质量如何，
以及 `## 待补充` 里列的"素材明确没记的点"——只有后者是**模型不可能自己知道**的信息。
新增 `GET /api/wiki/probe?q=` 探针（与图谱的 `recognize` 对称），注入内容第一次可以"看得见"。

两轮实测（同上口径，图谱两组都关）：

| 测试 | A（关 wiki） | B（开 wiki） |
| --- | --- | --- |
| 技术问题 · 缺口区分（严格口径：明说"你的库里没有记这一点"） | 0/3 | 2/3 |
| 技术问题 · 缺口区分（宽松口径：含"只记了 / 没展开 / 停在概念层"） | **3/3** | **3/3** |
| 元问题 · 点出具体缺口（"我库里还缺哪些关键点 / 最该补什么"） | 2/3 | **3/3** |

**诚实解读**：技术问题上两组在宽松口径下**完全一样** —— 笔记证据本身就薄（笔记#3 只有三个要点），
模型自己就能说"你只记了 QoS 可配置"。严格口径的 0/3→2/3 **有一部分是"我让它这么说它就说了"**
（注入里带了指令），所以不能当成"模型变聪明了"。**真正的差别在元问题**：B 组能把
"这一点在你的 wiki 里正标着「待补充」"说出来 —— 从"推理"变成"可引用的结构化事实"。

**顺带抓到并修掉两个真 bug**（都是这次才暴露的）：

1. **长页靠词频压掉对症的短页 → 直接制造幻觉**。问"关于 MQTT，我的知识库里还缺哪些关键点？"，
   注入的是 AI Agent / Docker 两个长页（各 7 分），**MQTT 页根本没进去**，模型于是声称
   "索引里没有 MQTT 页"——其实有（517 字、还带着待补充清单）。
   修法：排序改为**标题命中优先** → 分数 → 短的在前。
2. **局部目录被当成全集**。块里只列命中的前 2 页，模型会当成"知识库只有这些"。
   修法：表头写明**分母**——"本次命中的 2 页（知识库共 39 页）；没列出的主题不代表知识库里没有"。

（另修：缺口条目取行位移错了 1 位，输出过「充；QoS 的具体等级…」；wiki 页数从 1 放回 2 ——
近重复主题会让问题**正好命中那个没有「待补充」的页**，两条目录条目 250~350 字仍比原来一页 600 字便宜。）

**对 wiki 的结论**：它的位置是**元层**（目录 / 缺口 / 盘点 / 体检），不是证据层；
技术上它给不出增量，**关于"我库里有什么、缺什么"的问题才是它唯一能独立回答的问题**。
下一步要做的：主题去重、把 12 页 `quality=warn` 重生成、以及把"缺口"做成界面上的行动项
（而不是只塞进对话上下文）。

## 3. 被证伪的假设（也记下来，免得再试一遍）

### 放宽语义召回的专业带（0.08 → 0.20）：**失败，已回退**

假设：相对带当初是"没有重排时用来收紧尾巴"的替代品，现在有重排了，放宽一点让
"分数偏低但正确"的候选进池子，交给重排挑。

实测：85 条 recall 不变（0.976），**MRR 从 0.921 掉到 0.884** —— 池子里多了噪声，重排补不回来。
**结论：召回阶段收紧 + 重排挑选，这个分工是对的**；放宽带子是把噪声问题推给下一层，而下一层兜不住。

### 向量实体识别驱动图谱注入：**不可靠，已关闭**

曾经在精确识别为空时退回向量识别。实测问题：

| 问题 | 期望认出 | 实际认出 |
| --- | --- | --- |
| 让容器帮我管理对象有什么好处 | 容器 / IoC | **进入容器**（Docker/Git 语境，完全另一个概念） |
| 一堆字符串拼接用什么效率高 | StringBuilder | 无 |
| 类加载和内存划分 | JVM | 无 |

注入**错误概念的图关系**比不注入更糟（模型会顺着错误关系答）。所以注入只用精确/别名匹配；
`recognizeByVector` 保留为探针，要重新启用得先用"问题→概念"标注集把阈值标定出来。

## 5. 仍然存在的缺陷（诚实清单）

| 缺陷 | 现状 | 说明 |
| --- | --- | --- |
| **2 条用例始终召回不到** | 算法侧无法修 | 「物联网设备上报数据一般怎么做」「多个设备同时上报数据怎么保证不丢」期望 `note:3`(MQTT)。诊断结论：**问题里没有任何图内概念**（"物联网"不是节点，图里是 MQTT / IoT 低带宽弱网 / 消息协议），短语扩展无词可扩；而 bge-m3 对这个 98 字小节的打分（约 0.46~0.48）低于相对带。这是**内容/覆盖问题**：要么让这类概念进图，要么把那条笔记写到包含"设备上报"这类词 |
| **向量实体识别不可靠** | 已关闭注入 | 见 §3。要修得先有"问题→概念"标注集，属于另一个工程 |
| **PDF 表格丢结构** | 未解决 | `setSortByPosition(true)` 本来就开着；表格在纯文本抽取里必然被压平，需要表格感知的抽取器 |
| **分块参数没做 A/B** | 未做 | `TARGET=800 / OVERLAP=120` 仍是经验值，没做过 600/1000/1200 的对比 |
| **答案校验未接入界面** | 后端已就绪 | 校验结果已随 `AiChatVO.grounding` 回报，但前端还没把它显示成徽标 |

| **重排每次多一次调用** | 已知代价 | 约 1 秒/次。嫌慢可关（`kb.rerank`），关掉不会漏答案，只是答案可能排第 3、4 位 |

## 6.5 向量后端：MySQL 全扫 ⇄ Milvus ANN（可切换，默认仍是全扫）

**先纠正一个常见误解**：这个项目**没有向量数据库**。向量存在 `kb_chunk.vec`（float32 小端 BLOB，
配 `dim`/`model` 列），检索是"把全部块读进内存逐条算余弦"。这不是欠债，是取舍 ——
§4 的实测表说明扫描比一次查询嵌入便宜两个数量级。但**"以后会多"这件事必须提前设计**，
所以 2026-09-29 把向量层抽成可替换的，并接上了 Milvus（默认关闭）。

### 分工（这条分工决定了迁移成本）

| 角色 | 由谁负责 | 为什么 |
| --- | --- | --- |
| 块文本、来源、块 id、**一份 float32 向量** | **MySQL（权威）** | 检索结果要展示原文、要按来源过滤、要能重建；留着向量意味着**换后端不用重新嵌入** |
| "谁是近邻" | 向量后端（MySQL 全扫 / Milvus ANN） | 只有这一件事需要被替换 |

代码：`service/vector/VectorStore`（接口）、`MysqlVectorStore`（默认，含指纹缓存）、
`MilvusVectorStore`（REST，无新依赖）。检索的**阈值 + 相对带 + topK 一律在 `VectorIndexService` 里施加**，
两个后端共用同一口径 —— 否则"同一问题换后端命中不同"是最难定位的那类 bug。

### 为什么用 REST 而不是官方 Java SDK

`milvus-sdk-java` 会带进整套 gRPC + protobuf（十几 MB 依赖 + 版本对齐），而这套代码只用四件事：
建集合、插向量、删来源、查近邻。Milvus 2.4 起 v2 RESTful API 全覆盖，
用 JDK 自带 `HttpClient` 就够 —— **接 Milvus 没有引入任何新 Maven 依赖**。

### 运维形态与代价（诚实）

`docker-compose.milvus.yml` = **单容器**（Milvus 2.4 的 `etcd.use.embed=true` + `common.storageType=local`，
嵌入式 etcd + 本地磁盘），实测**启动 15 秒 healthy**，没有 etcd / minio 两个额外服务与两套备份。
官方的三容器形态（milvus + etcd + minio）只在需要分布式/多副本时才有意义 ——
个人知识库用不上，判据写在前面：**块数 >2 万（向量常驻 80MB+）或出现并发检索**时才值得切；

### 实测对照（2026-09-29，1296 块 / 1024 维，同一批问题）

| 项 | MySQL 全扫 | Milvus ANN |
| --- | --- | --- |
| top-5 命中集合 | — | **6/6 问题完全一致（连分数都相同）** |
| `eval?mode=vector` | recall@5 **0.866** / MRR **0.802** | recall@5 **0.866** / MRR **0.802** |
| 热态单查询（probe，中位数 5 次） | **111 ms** | 159 ms |
| 迁移成本 | — | `POST /api/kb/vector/sync`：1296 块 **10.9 秒**，**不重新嵌入** |

两个后端结果一字不差，说明"抽象 + 统一阈值口径"这层是干净的。
延迟上 **Milvus 反而慢 ~48ms**（多一次 HTTP 往返；两者都被 ~110ms 的查询嵌入主导）——
**现在切 Milvus 不是为了更快，是为了将来**（内存与并发），这个事实要写在前面，
免得过两天有人看到"上了向量库还是这个速度"以为是接错了。

### 故障与恢复（实测过的路径）

| 场景 | 行为 |
| --- | --- |
| Milvus 停掉 | 探活失败（30 秒缓存）→ 检索**自动降级**为 MySQL 全扫（实测仍返回完整命中）；检索时真的抛错会**立刻**标记不可用，不让每轮对话白等一次连接超时 |
| 状态如实报告 | `GET /api/kb/vector/status`：不可达时 `consistent=null`、hint 写"自动降级"；数量不一致时给出差值并指向 `vector/sync` |
| 恢复（容器重启） | 本地存储持久化，集合与向量都在 → `vectors=1296, consistent=true`，**不需要重新同步** |
| 停机期间写过索引 | 向量只落在 MySQL，`vector/sync` 补齐（**不是 rebuild** —— 那要重新嵌入，分钟级） |

### 开关与迁移命令

| 动作 | 命令 |
| --- | --- |
| 切后端 | `POST /api/kb/vector/backend?backend=milvus`（或 `PUT /api/settings {"vectorBackend":"milvus"}`） |
| **把已有向量灌进去（不重新嵌入）** | `POST /api/kb/vector/sync`（1.3k 块几秒；全量重建是分钟级） |
| 体检：两边向量数是否一致 | `GET /api/kb/vector/status` |
| 回退 | `POST /api/kb/vector/backend?backend=mysql` —— 立刻生效，因为 MySQL 那份向量一直在写 |

**降级是自动的**：配置了 Milvus 但探活失败（30 秒缓存）时，检索静默走 MySQL 全扫，
对话不受影响；Milvus 不可用期间写入的向量只落在 MySQL，恢复后 `vector/sync` 补齐
（`vector/status` 的 `consistent` 字段会显示漂移，**不允许悄悄不一致**）。

## 6.6 精排：有，但不是 Cross-Encoder（2026-09-29 补上 Cross-Encoder 并实测）

**先说结论**：召回 Top-K 之后**确实有精排**，但原来的实现是 **LLM 列表重排（listwise）**，
不是 Cross-Encoder —— 把候选（标题 + 120 字摘要）交给对话模型，让它输出 `{"order":[...]}`。
2026-09-29 抽出了 `Reranker` 接口并接上真正的 Cross-Encoder，用**同一批 97 条用例**做了对照。

| 精排后端 | 实现 | recall@5 | **MRR** | 97 条耗时 |
| --- | --- | --- | --- | --- |
| 关（基线） | — | 0.938 | 0.748 | 121s |
| `llm` | `LlmListwiseReranker`：对话模型输出 order 数组 | 0.938 | **0.902** | 204s |
| `cross` | `CrossEncoderReranker`：bge-reranker-base（278M，XLM-R）逐对打分 | 0.938 | **0.774** | 134s |

**实测结论（与直觉相反，所以更值得记下来）**：完整矩阵（同一批 97 条用例，mode=fused）：

| 精排配置 | recall@5 | **MRR** | 97 条耗时 |
| --- | --- | --- | --- |
| 关（基线） | 0.938 | 0.748 | 121s |
| `llm` @ 本地 qwen3:8b（改造前的默认） | 0.938 / 0.928 | 0.759 / 0.743 | ~5 min |
| `llm` @ deepseek-flash（**已采纳为当前配置**） | 0.938 | **0.902** | 204s |
| `cross` bge-reranker-base（120 字） | 0.938 | 0.774 | 134s |
| `cross` bge-reranker-base（600 字） | 0.928 | 0.789 | 196s |
| `cross` bge-reranker-v2-m3（120 字） | 0.928 | 0.822 | 184s |
| `cross` bge-reranker-v2-m3（600 字） | 0.938 | **0.843** | 369s |

三条结论：

1. **最大的收益不在换架构，而在换模型**：重排任务现在指向**本地 qwen3:8b**，
   两轮实测 MRR 0.759 / 0.743 —— 也就是"**几乎白干**"（其中一轮还低于不重排的 0.748）。
   把它指向 deepseek-flash，同一批用例 MRR **0.902（+15.4pp）**。
   重排这个活要的是"读得懂问题和候选的关系"，8B 本地模型做 listwise 排序明显不够。
2. **Cross-Encoder 用对了模型才有意义**：`bge-reranker-base`（278M）只有 0.774，
   而 `bge-reranker-v2-m3`（568M，多语言）到 **0.843** —— 同一套代码，只换模型 +13pp~7pp。
   原因基本可以确定是**跨语言**：查询是中文口语、片段常是英文 PDF 正文，
   base 版以英文语料为主，这类匹配是它的弱项。
3. **候选文本长度对 cross 有用、对 listwise 有害**（所以做成了设置 `kb.rerank_snippet`）：
   cross 从 120 → 600 字，v2-m3 是 0.822 → **0.843**；而 base 版 0.774 → 0.789。
   listwise 那边文本越长提示词越挤，默认保持 120。

**当前建议（已按第 1 条调整）**：重排指向**默认/deepseek-flash**（MRR 0.902，每问多一次调用）；
想省钱或离线时切 `cross` + v2-m3（0.843，完全本地、免费）。
指向本地 8B 是"省了钱但基本没效果"的组合 —— 这次实测把它从默认配置里去掉了，
`ModelRouting` 里 rerank 任务的默认类型也从 `local` 改成 `main`（免得以后有人又按"免费"改回去）。


**代码结构（照抄向量层那次的写法）**：

```
service/rerank/Reranker        接口：name / available / rerank / status
 ├─ LlmListwiseReranker        （原 RerankService 的逻辑整体搬过来，行为未改）
 └─ CrossEncoderReranker       （HTTP：POST /rerank，兼容 Jina/TEI/Cohere 形状）
service/RerankService          门面：选后端 + 回退链 + 状态
tools/rerank-server.py         sidecar：sentence-transformers CrossEncoder + 标准库 HTTP
开关：kb.rerank_backend = llm（默认）| cross    地址：kb.rerank_url（默认 http://127.0.0.1:8091/rerank）
```

**回退链（门面存在的主要理由）**：选中的后端失败 → 换另一个 → 都失败 → **原顺序**。
`cross` 探活失败（sidecar 没起）时 `active` 自动是 `llm`，状态里两个后端都报，
一眼能看出"这次到底用哪个重排的"。实测：sidecar 没起时 `cross.healthy=false / active=llm`，
检索照常（**不**每次白等一次连接超时 —— 这个坑在向量层踩过，这里一开始就规避了）。

**为什么 sidecar 而不是 JVM 内嵌**：这台机器 **Maven Central 不通**（加不了 `onnxruntime` 之类依赖），
而 Python 侧已有 torch 2.11+cpu / onnxruntime / tokenizers —— 起个九十来行的标准库 HTTP 服务是最短路径。

**速度**：cross 打 3 条候选 158ms；97 条整轮 134s（含嵌入与召回），比 llm 那轮（204s，跑在云端
deepseek-flash 上）还快；如果 llm 那轮用配置里的**本地 qwen3:8b**，97 条要**半小时以上**
（实测 25 分钟没跑完）。所以 cross 现在买到的是"**快而稳**"，不是"更准"。

**顺带记一个配置问题**：`ai.model_for_rerank` 原来指向 `f8c42ef9`，一个**已不存在的档案 id**
（现有档案只有 dd32310c / 09e70120 / addd41a4）。`ModelRouting.forTask` 解析不到就落到默认，
行为一直是对的（本地 Ollama），但配置本身悬空 —— 换模型时容易被它误导。


### 顺带补掉的两个生命周期缺陷

1. **按来源删除**：以前资料/笔记删掉后，ANN 库里会留孤儿向量（检索命中但补不到正文，
   表现是"结果莫名少几条、没有任何报错"）。现在 `deleteSource` 在增量索引的清理分支里同步调用。
2. **嵌入模型一致性**：换模型后旧向量与当前查询向量**不可比**（不同空间），
   以前会照算余弦出噪声；现在按行上的 `model` 跳过并记日志（Milvus 侧则因集合按模型分而天然隔离）。
