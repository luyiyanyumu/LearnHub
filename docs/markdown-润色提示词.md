# learn-hub 润色提示词 · 正式书面语版

> 与内置默认提示词最大的不同：**允许缩写**。内置默认写的是"严禁压缩与删减、字数不得少于原文"，
> 而本版允许在明确条件下缩写、也允许扩写。为此工程侧同步调整了长度守卫，见第 4 节。

---

## 1. 提示词全文（复制这一整段）

````text
你是资深中文技术文档编辑。任务：在不改变事实与逻辑的前提下，对给定的 Markdown 笔记做一次编辑加工。请严格遵守下列规则；凡本规则未授权者，一律不做改动。

一、基本约束
1. 只输出加工后的 Markdown 正文；不要输出解释、前言、结语、标题包装，也不要用代码围栏把整篇包起来。
2. 不得改变技术事实：数值、单位、参数、版本号、条件、例外、引用出处、代码逻辑一律保持原义。
3. 必须保留全部 Markdown 结构：标题层级、列表、表格、代码块、链接、图片、内联 HTML 标签（font / mark / u / sup / sub）、::: 提示块、details 折叠块，均按原样保留。
4. 不新增任何颜色、字号、加粗等格式；原文已有的格式不得删除、不得转移位置。

二、必须做的（逐项检查）
1. 修正错别字、语病、搭配不当、成分残缺。
2. 标点：中文内容一律使用全角标点；代码、命令行、文件路径、版本号内部保持原样。
3. 术语按附表统一，并统一大小写与中英混排空格。
4. 口语化表达改为书面语；含糊指代改为明确指代；冗长句拆为短句。
5. 同一段落内，若调整为「结论在前、依据在后」更清晰，允许调整语序；跨段落的顺序不得调整。

三、允许缩写（仅在下列情形，且必须同时满足第五节的硬性边界）
触发条件（满足其一即可）：
A. 同一信息在相邻位置重复出现两次及以上；
B. 纯口语填充词不承载信息（如「其实吧」「说白了」「这个东西」「大家注意一下」）；
C. 修饰语冗余（如「非常非常」「基本上可以说」），删除后语义完全不变。
做法：合并重复、删除填充词、压缩冗余修饰；允许长句改短句。不得减少信息点。

四、允许扩写（仅在下列情形，且必须同时满足第五节的硬性边界）
触发条件（满足其一即可）：
A. 指代不明（「它」「该方法」「这个」无法唯一定位）；
B. 省略前提，导致该句无法独立理解；
C. 术语首次出现时缺少必要界定或英文原文。
做法：补足指代对象、补足必要前提、补术语英文与简要定义。不得引入原文没有的内容。

五、缩写与扩写的共同硬性边界
1. 不得删除任何信息点。信息点指：技术事实、结论、依据、参数、数值、条件、例外、示例、代码、表格数据、链接、引用出处、操作步骤。
2. 不得删除任何段落、列表项、表格行、代码块、图片、提示块或折叠块；不得把两个并列项合并成一项。
3. 不得引入原文没有的技术事实、数值、结论、来源或示例；扩写内容必须能由原文直接推出。
4. 加工后的整体长度不得少于原文的 60%，也不得多于原文的 150%。
5. 任何规则与「保持原义」冲突时，以保持原义为准：宁可不改，不可改错。

六、术语与书写规范
maven→Maven、api→API、url→URL、javascript→JavaScript、jdk→JDK、jvm→JVM、jre→JRE、mysql→MySQL、redis→Redis、spring boot→Spring Boot、mybatis→MyBatis、vue→Vue、github→GitHub、html→HTML、css→CSS、json→JSON、sql→SQL、http→HTTP、npm→npm、node.js→Node.js、id→ID、ui→UI
中英文之间加一个半角空格；数字与单位之间不加空格（如 8GB）；中英文标点不得混用。

七、不确定时
1. 无法判断改动是否改变原义 → 保持原文不动。
2. 专业术语不确定 → 保持原文写法。
3. 原文已符合全部规则 → 原样返回；不得为了「看起来改过」而改写。

八、关于片段
若输入以「【这是全文的第 i/n 段…】」开头，说明本次只处理该片段：只加工片段本身；不得添加「综上所述」这类总结性结尾；不得提及分段；不得改写与相邻片段衔接处的措辞。
````

## 2. 为什么这样写（消歧手法）

「必要时可扩写或缩写」这句话本身是有歧义的——什么叫"必要"？不同人、不同次调用会得到完全不同的结果。
本提示词用四种手法把它变成**可判定、可复现**的规则：

| 手法 | 具体做法 |
| --- | --- |
| 触发条件化 | 把"必要时"拆成可枚举的条件（重复、填充词、冗余修饰 / 指代不明、缺前提、缺界定），逐条列出 |
| 以"信息点"替代"字数" | 缩写标准是**信息点不减少**，而不是字数达标——避免模型为凑字数注水，也避免它拿字数当免罪符 |
| 双边界夹逼 | 下界 60%（不许大砍）、上界 150%（不许灌水），中间留出合理的改写空间 |
| 冲突时优先级明确 | 明确规定"任何规则与保持原义冲突，以保持原义为准"，避免规则打架时模型自由发挥 |

另外三处刻意留白：

- **不注入术语表之外的知识**：明确禁止"引入原文没有的技术事实"，防止润色变成"顺手补充内容"而引入错误。
- **不确定时不动**：这是纠错场景下最安全的默认值，宁可少改。
- **原文已合规就原样返回**：明确禁止"为了看起来改过而改写"，避免无意义抖动。

## 3. 与内置默认提示词的差异

| 项 | 内置默认（`DEFAULT_POLISH_PROMPT`） | 本版 |
| --- | --- | --- |
| 缩写 | **禁止**："严禁压缩与删减""字数不得少于原文" | **允许**，但限定触发条件 + 信息点不减少 + 长度下界 60% |
| 扩写 | 未提及 | **允许**，但限定触发条件 + 不得引入新事实 + 长度上界 150% |
| 术语表 | 只举例（maven→Maven 等 4 个） | 22 条固定映射 |
| 冲突处理 | 未规定 | 明确规定"以保持原义为准" |
| 分段场景 | 未提及 | 明确片段处理规则（与工程分块策略对齐） |

> 结论：默认版是「只准改语言、不准动篇幅」；本版是「篇幅可变，但信息点与事实不可变」。
> 两者都自洽，按需要选一个——**不要混用**，否则模型会同时收到"不许删"和"可以删"两条指令。

## 4. 与工程实现的关系（必须一起看）

实现位于 `backend/src/main/java/org/dyh/learnhub/ai/AgentService.java` 的 `polish()`：

| 机制 | 取值 | 与本提示词的关系 |
| --- | --- | --- |
| 分块阈值 | `POLISH_CHUNK_CHARS = 4000` | 超过 4000 字会切片，每片独立调用；故提示词第八节规定片段行为 |
| 单轮预算 | `ROUND_BUDGET_MS = 270000`（270s）、`MIN_STEP_BUDGET_MS = 30000` | 段数多时可能提前失败并提示"分段选中后再处理" |
| 长度守卫 | `POLISH_MIN_RATIO` | 输出短于原文该比例 → 判定为"疑似缩水"并**静默回退原文** |

**这里原有一个冲突**：守卫原值为 `0.75`，而本版提示词允许缩写到 60%。若模型按提示词缩写到 65%，
守卫会判定"缩水"，把结果丢掉并返回原文——用户看到的是"处理完成但内容没变"，
既无明显报错，也无从判断原因。

因此配套调整：**`POLISH_MIN_RATIO` 由 0.75 下调为 0.6**，与提示词的长度下界对齐。
守卫仍然有效（它防的是模型输出被截断这类真实故障），只是不再把"合规的缩写"误判成故障。

> 如果你希望更自由地缩写，可以在设置里改提示词的长度下界，但**必须同步调低这个常量**，
> 否则改动不会生效。二者是一对，不能只改一边。

## 5. 使用方式

1. **改技能文件**：编辑 `skills/markdown-polish/SKILL.md` 的正文 → 存盘即生效，不用重启后端。
   - 长度下界写在 frontmatter：`min_ratio: 0.6`，后端长度守卫直接读它。
2. **或在设置 → 技能里点「替换」上传 `.md`**：正文会替换掉 `SKILL.md`，元数据默认沿用原值。
3. **加一套新规则**：用「上传技能」新建 `skills/<新目录>/SKILL.md`（frontmatter 写 `applies_to: polish`）；
   两套规则**不要混用**（见下节结论）。

## 6. 自检清单（改完提示词后过一遍）

- [ ] 缩写是否有明确的触发条件，而不是"必要时"
- [ ] 是否用"信息点"而非"字数"作为缩写标准
- [ ] 是否给了长度上下界，且与 `POLISH_MIN_RATIO` 不冲突
- [ ] 是否规定"规则冲突时以保持原义为准"
- [ ] 是否禁止引入原文没有的技术事实
- [ ] 是否说明了分块（片段）场景下的行为
- [ ] 是否要求"只输出正文、不要前后缀与整篇代码围栏"
- [ ] 与内置默认提示词是否**只启用了一个**（不要混用两套矛盾规则）
